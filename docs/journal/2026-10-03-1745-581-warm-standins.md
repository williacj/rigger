ABOUTME: Journal for #581 (M4-F26): why every helper that writes an executable stand-in now warms
it before returning, what the warming run must not leave behind, and what was left out and why.

# #581 — every stand-in is warmed before its first use

**What changed.** `fixture` now runs `warmed` on the script it writes. So does every other helper
under `test/` that writes an executable a test, or the code under test, runs as a command: `stubGh`
(and with it `stubClaude`), `installStandInAgent`, `installFakeGh`,
`installGhRefusingStreamAfterMove`, `installAgentCli` in `once`, `run` and
`worktree-root-inside`, `recordingPs` and `hangingStartPs` in `maker-dispatch`, `recordingPath` in
`report`, and `waiter` in `process-adapter`. Each stand-in's first line after its `#!` is now
`EXIT_IF_WARMING`, or for a Node entry `process.env.RIGGER_FIXTURE_WARMING ||` before its import,
or for the compiled waiter a `getenv` check. So the warming run exits before it records a call,
writes a marker, reads a plan or loads a module.

**Why the guard comes before the import.** A Node stand-in that imports this repository's test
modules loads `test/process-fixtures.mjs`, whose module body runs `which git`. `warmed` hands the
stand-in an environment holding only `RIGGER_FIXTURE_WARMING`, with no `PATH`, so that import
fails. The red runs showed it: `Error: Command failed: /usr/bin/which git`. A guard inside `main`
would also have paid a whole module load on every warm.

**Renames and rewrites stay warm.** `stubClaude` renames `stubGh`'s `gh` to `claude`. A probe in
the scratchpad (`c581-probe.mjs`, not committed) measured 15 rounds of each case with Node 26.5.0 on
macOS 27.0 on 2026-10-03, at a one-minute load of 22.5. The median first exec of a fresh shell
script took 142 ms, and a second exec 5 ms. A warmed file that was then renamed took 5 ms, and so
did a warmed file rewritten in place. A Node-shebang script took 183 ms on its first exec and 37 ms
on its second. So `stubClaude` needs no warm of its own, and a test that rewrites its stand-in
does not lose the warmth.

**Left out, and why.**
- `test/suite.sh`'s refusing `gh`, `claude` and `codex`. No test means to run them; a run of one
  fails the suite. A warming guard in them would give any environment that sets
  `RIGGER_FIXTURE_WARMING` a way to pass them silently, which weakens the net they are.
- The installed `rigger` that `installFromTarball` gets from `npm install`. It is the code under
  test, not a stand-in, and a guard there would mean changing `src/cli/rigger.mjs`, a self-hosting
  path the card does not list.
- Scripts handed to an interpreter as an argument (`outliving`'s `/bin/bash script`, the perl
  programs), and the files `process-adapter` writes to prove an exec fails. The card puts both
  outside.

**The compiled `ps` keeps its own `warmed(ps)`.** It is built inline in its one test at
`test/process-adapter.test.mjs`, not by a helper, so no default reaches it.
