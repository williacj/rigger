# The escalation route

B7, M6 revision 4's recut of M6-20a, listed "the destination function, the `raiser` field, the
maker-of-the-kind rule, the routing-comment check, and the routing comment itself". K66 gave the
card `R-ESCALATE-22`. U42 kept the live config's `escalate` line out until the M6-close
promotion, so `rigger.config.mjs` and its template are unchanged.

The routing comment's post moves from B7's 20a to M6-20b. The architect's pre-dispatch attack
(998#6430436314) ruled Q1 sound: the comment is the record that a card went to a role, so posted
with no dispatch behind it, the record would be false, and the post and the dispatch are one
ordered step that L3's attempt owns. This card fixes the comment's first line and finds the
comment by it, and M6-20b posts it.

K96 took the attack's finding 3, option (a). L3 dispatches no role yet, so an escalation the
function sends to a role still goes to the owner. The owner's comment names the role it was not
sent to, and the `review.escalate` event records the function's answer as `destination`.

The function sits in `src/workflow/escalation.mjs`. `nextAction` calls it for the loop's
escalations with only the category and raiser, since a loop-raised escalation goes to the owner
and reads no comment. `settled` calls it for a maker's note with the issue comments it already
read for the note, and the card's kind as `kindOf` selects it. `src/workflow/judges.mjs` does not
change: its three escalate answers reach a caller only through `nextAction`, which adds the
destination.

The rows marked "verb" run through `rigger once`, whose stand-in maker writes a `critical` note.
`critical` goes to the owner before the configured destination is read. That test shows the
destination reaching the event and the comment through the real bin. The function and settle
tests carry the `ambiguous` cells of the key-absent rows.
