## What the side does

`pushStream({ repository, stream, emitter, limit, spawn, now, environment })` makes each `git`
call through `spawn`. Unless the caller hands another, that spawn is `runCommand`. Each call gets
one argument object: `timeout` holds what is left of `limit`, and the emitter is the one the side
was handed. The environment is `gitEnvironment(environment)` with `GIT_TERMINAL_PROMPT=0`. The
side answers `{ outcome, bytes, parent, commit, reason }` and records nothing itself.

**The fetch's flags.** The fetch is `git fetch --no-write-fetch-head --no-tags origin <tip>`.
`--no-write-fetch-head` is what keeps it from writing `FETCH_HEAD`, and `git` has had it since
2.29 (P25). `--no-tags` stops tag auto-following, so the fetch writes no ref at all ("The steps",
step 3). A sha named with no destination writes no ref under any refspec.

**How the side tells a tip is missing.** The calls the card allows include none that asks,
in words that do not depend on the locale, whether the store holds an object. So the side tries
`commit-tree` onto the tip first. Where that fails and a `commit-tree` with no parent succeeds, the
tip is the missing piece, and only then does the side fetch it and build again. Where the commit
with no parent fails too, the failure is not the tip's, and the push answers `failed` with what
the first `commit-tree` printed. That leaves a commit object with no parent in the store, which
no ref names. The step order is then `ls-remote`, `remote get-url --push --all origin`,
`hash-object`, `mktree`, `commit-tree`, and on a missing tip a `commit-tree` with no parent,
`fetch` and `commit-tree` again, then `push` to the one push URL.

## The git output the controlled doubles copy

Measured with `git` 2.54.0 (Apple Git-157) on 2026-10-28, in a throwaway scratch directory
against a local bare origin:

- `git push --porcelain` of a new ref printed `*\t<c>:refs/rigger/events\t[new reference]`, then
  `Done`, and exited 0. An update printed a space flag and `<old>..<new>`.
- A push onto a tip the pusher lacked printed `!\t<c>:refs/rigger/events\t[rejected] (fetch
  first)` and exited 1.
- `git commit-tree <tree> -p <tip>`, where the store lacked the tip, printed `fatal: <tip> is not
  a valid object` and exited 128.
- `git fetch --no-write-fetch-head --no-tags origin <tip>` fetched the tip by its name, left no
  `FETCH_HEAD`, and changed no ref.

**I2's text.** "Non-fast-forward" is the word `git` prints only where the pusher holds the tip
that beat it. A tip it lacks reads "fetch first", as measured above. So I2's other writer works
in the pushing repository. Both are `[rejected]` statuses, and both answer `refused`.

## P26: cases no row decides

These are the cases I met:

- **A failure that is not a refused event.** A rejection from the spawn other than
  `EVENT_REFUSED`, `NOT_STARTED` included, answers `failed` with its message (P11).
- **A tip held, with `commit-tree` failing anyway.** This is the probe case above. It answers
  `failed` with `commit-tree`'s text, and it makes no fetch.
- **A missing tip whose fetch succeeds, and a `commit-tree` that fails again.** It answers
  `failed` with the second `commit-tree`'s text. The P26 test in `test/data-ref.test.mjs` holds
  this, and so holds that no `git push` follows.
- **`ls-remote` printing both the data ref and a colliding ref** (P7 and P16 with the data ref
  present). The answer is `failed`, and it carries `parent`, because the read succeeded and "The
  outcome" leaves `parent` out only where the ref was absent or the read failed.
- **More than one colliding ref.** The reason names the first one `ls-remote` printed.
- **`git remote get-url --push --all origin` printing no URL.** The push answers `failed`, saying
  origin has no push URL, because the side needs exactly one (reading 8).
