ABOUTME: Journal for #515: restart-kill's command-exits-after-SIGKILL test hung because one
open-and-close of a FIFO can leave its reader blocked for ever; the release now writes a line.

# #515 — the FIFO release a reader can miss

**The wait that never settled was the wait for the command to exit.** The log of the cancelled run
on `9157cd0` names no wait, so the hunt had to cause the hang again. A copy of the test file,
holding up to 31 copies of the test, was run inside whole suites at base `4f017db`. Each of the four
waits recorded which one it was on, and a dump ran when the test ended. Of about 600 runs of the
test inside suites whose results were read, started at one-minute loads of 16 to 104, one timed out
after 60 s, in a suite started at a load of 33. Its dump said it was on `leaderGoneAfterDeath`'s
wait for the command to exit. The command was alive, sleeping, and reparented to pid 1. `exit-now`
and `ready` were both there. So the test's open and close of `exit-now` had already happened, and
the command never went on. 360 runs of the test alone, six at once, never hung.

**The FIFO release alone reproduces it.** A spike ran a shell `read line < fifo; exit 0`, with Node
retrying a non-blocking write open each turn and closing it at once, as `opened` did. Over 5,800
readers, 5 were still alive 3 s later, every one at a load of 40 or more; at a load of 12, 300
readers showed none. For the 3 stuck readers read with `lsof`, it listed the FIFO as the reader's
standard input, so its open had finished and it was blocked in `read`. The writer had found it
within 3 to 28 tries.

**Why the reader misses the close is an inference.** It is inferred, not measured, that the writer's
open and close land while the reader's open is still under way, and the end of input is lost there.
The kernel was not traced. What is measured is the end state: an open reader blocked in `read` with
no writer left.

**The fix writes the reader a line, and waits for it to leave.** `opened` writes a newline each turn
an open finds a reader, and settles only once an open finds none. A read returns a line however the
close went, so a reader the close missed still goes on. `ENXIO` after a reader was found means that
reader has closed the FIFO. Waiting for that keeps the wait for the command's exit from starting
while the command is still blocked.

**The forcing holds a second writer open.** Once the command is a reader, the test opens a writer of
its own and keeps it until teardown. To the command's read, that writer is the close it never saw,
so no end of input comes. That is the stuck reader's end state, made by ordering from the test, with
no sleep and no timer. At the base, the old release leaves the command blocked, and the test times
out on the same wait. At the head, the line goes through the held writer's FIFO and the command
exits. A new test keeps this forcing as a regression test of `opened` itself.

**Naming the waits needed a diagnostic, not an error.** Once `node:test`'s timeout has failed a
test, an error the test function throws afterwards never reaches the report. An after hook that
throws does not either. A `t.diagnostic` added when the test's signal aborts is printed under the
failed test. So `awaiting` wraps each of the four waits, and `until` itself is unchanged.

**What the hunts cost.** The suite hunts drove the host's load to about 100 at times. They also
showed failures this card did not cause: `directory-census.test.mjs` at :360, :370, :382, :393 and
:449, `process-adapter.test.mjs:2013`, and `restart-kill.test.mjs:260`, each in a suite started at a
one-minute load of 28 or more. The PR names each one with its output. The logs of the first hunt's
twelve suites, and of two suites of the second, were lost when a later hunt cleared their directory.
Only the first hunt's `directory-census.test.mjs:382` failure was read before that, and its output
in the PR is a reconstruction from that reading.
