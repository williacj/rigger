# #433 — L3 drives an attempt, one step at a time

**The attempt.** `loop` now has L1 make the attempt's workspace through an injected handle
(ruling 5, P4). It dispatches each step L2's next action names, one at a time, under an id L3
allocates. Its L3 `dispatch` event is recorded before L1 acts. Each outcome goes back to `decide`
unread. An answer with no step is the maker. With no maker injected, the pull answers that the card
reached it, naming the card and its workspace, and the card stays in Coding. `settled` takes the
maker's outcome alone.

**A path the table had no line for.** L1's `dispatch` needs the state directory that holds its
record of process groups. Nothing `loop` was handed carried it: not the config, not the sink, and
not the kill, which closes over it. The card's grant table allowed each harness's `loop` call to
gain only the workspace handle. So the maker stopped twice before writing code, and asked.

- Ruling 10 has `loop` take `state` and refuse a missing or bad one when built.
- The owner granted the extra argument on the three harness lines that needed it.
- `test/loop.test.mjs:1162` needed nothing. `claiming` refuses the missing kill before `loop` checks `state`.

**A test that raced L1.** The first version of the record-refusal test had its step make
`groups.json.partial` a directory at once. L0 hands L1 the group only after it has read the
command's start time, so on one run the step won. `addGroup` then failed with a raw `EISDIR`, and
the test's `RECORD_REFUSED` never arose. The step now waits until the record names its own group
before it blocks the write. That is a fault in the test, not in the product, and this card
introduced it.

**Found outside the acceptance, and not built:**

- `test/step-restart-kill.test.mjs` repeats a compact form of `consumerIn` and its first-call
  `gh` from `test/restart-kill.test.mjs`. Extracting both into one module would change
  `restart-kill.test.mjs`, which the table does not name.
