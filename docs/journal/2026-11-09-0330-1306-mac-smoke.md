# Hosted macOS smoke job

The plan mode cannot stand in for "not journal-only". An owner's `ci:full` label on a journal-only pull request plans `BROAD_EXECUTED`, and an `INVALID` plan says nothing about the change. So the plan now publishes `journalOnly` beside its mode, from the same predicate the mode uses, and the smoke job reads that output rather than the mode.

The first review found that `journalOnly` still hung on the forge API. Where an API read failed, the collected facts held no change list, so the output said `false` and a journal-only pull request started the job. The plan now classifies the checkout's merge against its first parent from Git alone, which needs no API answer.

The smoke job checks out the commit the plan verified and runs whether or not the plan succeeded. Where Git cannot classify the change either, or the plan published nothing, `journalOnly` is not `true` and the job runs: a job no required context waits on costs a runner, not a merge.

The card said it rewrites no existing test. Adding a job does change two existing assertions that pin `ci.yml`'s job list, in `test/workflow-files.test.mjs` and `test/ci-proof-source.test.mjs`; the second sits outside the card's "Lands in", so the owner granted both lines before they were pushed.

The first review also found the tests bypassed the job-output mapping that carries `journalOnly` to the smoke job. A test now runs the plan step's command and carries its output through that mapping, as the runner does.

The smoke set needs real macOS tools, `test/verify-mac-containment` among them, so a Linux host proves only the workflow wiring. The time budget is proved by the hosted runs at the pull request's own pushes.
