# Clock arming

## What the tests recorded

A16's world, run at the head with its stream printed, recorded these L3 events at its start. The
record held armings of `rescheduled` (every 2 s), `caught` and `skipped`, all at 12:00:00, and the
start fell at 12:00:05.500 with `fresh`, `rescheduled` and `caught` under `catchUp: 'fire'` and
`skipped` under `skip`:

```json
{"ts":"2026-10-29T12:00:05.500Z","run":"r-arming","layer":"L3","event":"run.start","concurrency":1}
{"ts":"2026-10-29T12:00:05.500Z","run":"r-arming","layer":"L3","event":"trigger.armed","name":"fresh","interval":1000,"anchor":"2026-10-29T12:00:00.000Z"}
{"ts":"2026-10-29T12:00:05.500Z","run":"r-arming","layer":"L3","event":"trigger.armed","name":"rescheduled","interval":1000,"anchor":"2026-10-29T12:00:00.000Z"}
{"ts":"2026-10-29T12:00:05.500Z","run":"r-arming","layer":"L3","event":"trigger","trigger":"clock","name":"caught","occurrence":"2026-10-29T12:00:05.000Z"}
{"ts":"2026-10-29T12:00:05.500Z","run":"r-arming","layer":"L3","event":"trigger.outcome","name":"caught","occurrence":"2026-10-29T12:00:05.000Z","outcome":"job"}
{"ts":"2026-10-29T12:00:05.500Z","run":"r-arming","layer":"L3","event":"trigger","trigger":"pull"}
{"ts":"2026-10-29T12:00:05.500Z","run":"r-arming","layer":"L3","event":"trigger","trigger":"drain"}
```

The `trigger.armed` of `fresh` is one arming, and `caught`'s `trigger` and `trigger.outcome` are
one catch-up firing, carrying the newest of the five occurrences missed since its last arming.

## Cases met under A20

- **The order at a start.** `run.start`, then the read of the record, each arming, the settling of
  each `report` firing found pending, then the clock's first wake, which makes each catch-up
  firing, and only then the start's first pull. `run` awaits that first wake before it pulls, so
  A7's catch-up firing always precedes the first pull, as the stream above shows.
- **The arming's instant.** It is the `trigger.armed` event's `ts`, which L3 reads back from the
  record once the sink has written the event. L3 does not read its own clock for it: one clock read
  twice, once by the sink and once by L3, can move between the reads, and the round-1 architect
  judge showed that an occurrence at that later instant was then skipped. Where the stream does not
  hold the arming, as when the sink still holds its events unnamed, L3 falls back to its clock read
  after the append.
- **The start's instant.** Under `catchUp: 'skip'` an occurrence is missed, and so never fires, only
  where it falls at or before the instant the start read the record, which L3 reads just before it.
  An occurrence that comes due while the start arms is after the start, and fires at its first wake.
- **No trigger declared.** A start under `run` with no clock declaration, or an empty trigger set,
  still reads the record, settles each `report` firing found pending as abandoned, and hands an
  unreadable record to the verb. It arms nothing and fires nothing, and a refused abandoned outcome
  stays pending for the pull trigger to settle.
- **What a recorded event is.** `readEvents` refuses only a line that is not JSON, so the start
  decides in one place, `unlikeEvent` in `loop.mjs`, what each line it reads must hold. The check
  accepts exactly what L3 and the sink write from any config the validator admits, and refuses only
  lines they can never write. Every line holds the envelope: `ts` an instant exactly as
  `toISOString` spells it, six-digit years past 9999 included, a non-empty `run`, a layer `L0` to
  `L5` and a non-empty `event`, and a `trigger` names its trigger. An arming, a clock firing's start
  and an outcome are L3's: a name, any string, since a trigger's name is any key of the config, the
  empty one included; an arming's `interval` and `anchor` as `validate.mjs`'s `schedule` admits
  them; a start's or outcome's `occurrence` as an instant; a start's `after`, where present, a whole
  number; an outcome one of `job`, `failed`, `abandoned` or `card`, a card outcome naming its
  issue. Any other line makes the record unreadable, named by stream and line, and nothing arms or
  fires for the run. `card` and `dispatch` are read by no clock rule, so the start does not check
  them.
- **A refused arming.** The trigger whose `trigger.armed` the sink refused fires nothing for the
  run's life, since arming happens only at a start; each other declared trigger still tries its
  own arming, as "Failure model" has each start try its own event.
- **A pending `report` firing's occurrence.** L3 counts it as the trigger's last firing from the
  start on, so where the sink refuses its abandoned outcome, that occurrence never fires again once
  a later trigger settles it.
- **An anchor compared as written.** L3 compares a trigger's `anchor` with its newest arming's as
  the config spells it, so an anchor rewritten at another offset naming the same instant re-arms.
- **A card-shaped firing pending at a start (A18, out).** Its start carries `after`, so this card
  neither settles it nor counts its occurrence as a last firing. Should that trigger now declare
  `report` at the same schedule, the occurrence could fire as a report; M7-22b's settling of the
  card-shaped firing decides it first.
- **Card-shaped occurrences before M7-22b.** This card arms card-shaped triggers and fires none of
  them. Once M7-22b merges, an occurrence that came due between the two is missed at the next start
  under `run`, and its catch-up policy decides it.
