# #440 — A loaded host ends every pause late, and the write kept room for one

## The cause

`writeWhole` begins a pause only where it would end `SPARE` (100 ms) before its deadline. That
covers a last pause that ends up to 100 ms late, and nothing more. A host loaded for the whole of
the wait ends every pause late, not only the last, and the write had already seen each earlier
pause end late before it chose to begin the last one. It went on keeping 100 ms in hand
regardless.

Two recorded failures ran past the bound under load, and neither was on this host:

- 1,058.5 ms at a one-minute load of 82, after PR #421;
- 1,002.97 ms in `:490`'s untouched case at a load of about 118, on PR #531.

Neither log holds a trace. So they cannot show whether the pauses before the last ran late, or
whether only the last one did. The cause here is argued from the code and from forced traces,
not from those logs.

## How the forcing showed it

The forcing makes each `Atomics.wait` in the child end 250 ms late on the child's clock, which
stands in for a loaded host, and changes nothing else. A preload set it in the existing tests'
children, and the new regression test sets it in its own child.

At base `cdbd247`, under that forcing, the never-touched end-only test (`:490`, S3) took 1,006.58
to 1,007.15 ms, failing its `took <= UNDRAINED_BOUND` assertion in 5 of 5 runs. The traces show
the same sequence in every run: one write of 8,192 bytes, then `EAGAIN`, then four pauses each
taking 251.0 to 251.5 ms on the child's clock. In the first run the fourth pause began 755.43 ms
after the call. That was within the 899 ms the old rule allowed, so it ended past the bound, and
the write gave up at 1,006.47 ms. Of the time measured, 0.17 to 0.19 ms fell outside `writeWhole`,
so neither the fixture nor the test's own measure is where the time went.

At the head, under the identical forcing, the same test took 755.09 to 755.63 ms in 5 of 5 runs.
After three pauses had each ended 250 ms late, the write would not begin a fourth.

## The fix

The write keeps the greater of `SPARE` and the latest any of its pauses has ended past `PAUSE`.
Pauses that end less than 100 ms late leave the write exactly as it was. Over 20 natural base
runs and 5 natural head runs at loads near 2, every undrained end took 899.2 to 900.8 ms.

## What stays open

A host that holds only the last pause, longer than any pause before it, still holds the write
past the bound. Nothing in the write can see that coming, and the code comment says so.

The 300 ms held-open test (`:514`, S5) admits only 200 ms between its lower and upper guards. So
where every pause runs late by more than about 200 ms, no choice of when to give up lands it
inside both guards. Under the 250 ms forcing it took 804 ms at the head, inside them.
