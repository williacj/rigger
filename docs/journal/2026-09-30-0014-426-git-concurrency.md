# #426 — Which git operations fail at once, measured

The report is `docs/spikes/git-operations-at-once.md`.

## What we learned

Fetch, worktree creation with tracking, and prune fail when several run at once on one
repository. Removal, branch reset and branch delete did not. A `git commit` holding its ref locks
in another worktree broke nothing, and nothing broke it. A worktree costs about 57 ms to make and
51 ms to remove here, so a queue is cheap.

The failure the queue cannot cover is a fetch. An agent fetching in its own worktree made
Rigger's fetch fail in 12 of 20 rounds, because both update the same remote-tracking ref.

## What nearly misled us

**Twenty clean rounds are not evidence of a race-free operation.** Creation without tracking
passed 20 rounds at 6 at once, then failed 5 times in the next 600. The failure rate was about
0.3%, and a 20-round bar reads it as zero.

**A held commit has to be held by its locks.** A `pre-commit` hook holds none. A
`reference-transaction` hook waiting in `prepared` does hold them, and a listing of the common git
directory showed both lock files present for the whole of every operation.

**Naming shapes the result.** Branch names sharing a directory, as `p/…` did in the harness, let a
delete remove the reflog directory an add was about to write into. Rigger's topics hold no `/`,
so its branches never do. A harness's naming can manufacture or hide a race, so match the
names the product will use.

**A fetch into a ref of your own still writes the remote-tracking ref.** Fetching from a named
remote updates that remote's tracking ref as well, so it contended with the agent's fetch exactly
as before.
