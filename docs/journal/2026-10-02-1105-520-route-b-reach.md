# #520 — a Claude Code judge reaches `head` by route B

**Route B held on the first live run, so route C stays the recorded fallback.** The gated run
(`test/provider-claude-reach-live.test.mjs`) started three sessions with `reach` naming a planted
`head`, on Claude Code 2.1.287 under `sonnet`. Nothing of `head`'s was listed or named, and no hook
or MCP server of its started. The agent could not be dispatched, and the work ran with no
permission denied. The shell's directory reset to `main` after each Bash call, as #519's c8 found,
so each command reaching `head` is one line, `cd <head> && <command>`, whose parts each have a rule.

**The commands a role runs are the ones the consumer's own settings allow.** The adapter has no
other list of them: ruling 1 Q1 has the consumer's provider settings decide what an agent may run
unprompted, and the template writes one rule per command (`Bash(npm test:*)`). So the grant adds
only `Bash(cd <head>)` beside the `Read` and `Edit` rules. A declared rule naming a compound line is
refused when `reach` is given, rather than carried, because c17 found such a rule admits nothing
and the card's acceptance has the settings hold none. This is my reading of "a rule of its own for
each command the role runs", and a judge should rule on it.

**The `cd` rule is built from a path, so the path must be plain.** Codex's round-1 review found
that a real directory named `head;echo` made `Bash(cd …/head;echo)`, a compound rule, and so a
command the consumer's settings never allowed. The adapter now refuses a reached directory whose
real path holds anything but letters, digits and `/._+-`. A space or a quote would also fail
quietly the other way: the session types the path quoted and the rule names it bare. #534's
engineer judge then found the same gap in the path rules: a `*`, `?`, `[` or `]` in the path makes
`Read(/<head>/**)` match directories beside it. The one allowlist covers all three classes, and
each class has its own test.

**The compound check first missed a lone `&` and a line break.** The engineer judge found
`Bash(npm test & echo x)` carried across, and a live session denied that very command as using
"the `&` background operator". The check now reads any of `;`, `&`, `|` or a line break as a
list or pipeline operator. It reads characters, not shell syntax, so a quoted pipe such as
`Bash(grep -E 'a|b' x)` is refused too; that fails closed with the rule named.

**Both live mutations redded the run for the reason meant.** Adding `--add-dir <head>` (route A)
redded all three tests on "head's agent was listed": the `init` record's `agents` held
`c520-head-agent`, as #519's c2 found. Dropping the `Read` and `Edit` rules redded only the work
test, on "the file only head holds was not read".

**The trust warning is expected.** Every session printed "Ignoring 2 permissions.allow entries from
.claude/settings.json: this workspace has not been trusted". The same rules reach the session
through `--settings`, which #480 measured honoured, and the runs used them.

**The working directory's own sources still load under route B.** The card's author added ruling
8's item 5 under `R-LOOP-6`. In the live run, `main`'s `SessionStart` hook wrote its file, its
`.mcp.json` server was connected (source `dynamic`, through `--mcp-config`), and the session named
its `CLAUDE.md` marker. Dropping `--mcp-config`, and separately setting `disableAllHooks`, each
redded all three live tests on the matching assertion.

**The consumer's deny rules now reach `head` too (O61, ruling 12).** The engineer judge measured
`Read(./.env)` and `Read(**/.secret)` protecting `main`'s files and not `head`'s. The invocation now
writes each path-relative deny rule again, anchored at each reached directory, depth for depth: a
bare name at any depth, a multi-segment pattern at its place. The live run was denied `head`'s
`.env` and `.secret`.

**An inline `/path` rule does not hold at the working directory.** A probe on 2.1.287 passed
`Read(/secret.txt)` only inline in `--settings`, and the session read `main/secret.txt`. The same
rule in the project's own `.claude/settings.json` denied it, so an untrusted project's own deny rules
are honoured even though its allow rules are not. Where the inline rule resolves was not settled:
`/etc/hosts` is refused anyway, outside the working directories, so that probe could not tell. The
adapter anchors each `/path` rule at `main` and at each `head`.

**The `cd` rule is gone, and a space is admitted.** With only the two path rules, the session ran
`cd "<head with space>" && npm test` with no denial, as the engineer had measured for a plain path.

**`./.env` blocks at every depth, not at the top.** The engineer judge measured on 2.1.287 that
`Read(./.env)` denies `sub/.env` too, while the copy denied only `head/.env`. My probe on 2.1.288,
which the host moved to during the card, agreed, and found a multi-segment rule anchored with or
without `./`: `Read(./a/b.txt)` and `Read(a/b.txt)` each denied `a/b.txt` and not `x/a/b.txt`. So
`./` is dropped before the depth is decided, and a live case now reads `head/sub/.env`.
