# 2026-09-25 — L3 claims without dispatching

`src/scheduling/loop.mjs` now exports `claimOnly` beside `loop`. It takes everything `loop`
takes except the dispatch, and answers a handle whose `claim(limit)` claims up to `limit` cards
and never more than N. It moves each claimed card through L2 and answers the cards. `once` will
pass 1 and `run` will pass nothing.

**It is a separate export, not a method on `loop`'s handle.** Rule 8 of the boundary test fails
any module outside `src/scheduling/` that binds `loop`. A verb therefore could not reach a method
on the object `loop` returns. `claimOnly` never names `loop`. A test in `test/loop.test.mjs` runs
the real boundary report over the source tree plus a `src/cli/` module that imports `claimOnly`
and calls it, and the report is clean. The same test shows that importing `loop` from that
module still breaks rule 8.

**The loop and the claim-only call share one set of steps.** The read-and-claim step, the start
and the slot release now live in one internal function, `claiming`. Both callers use it, so
nothing is copied. A consequence is that the claim-only call records its events in `pull()`'s
order: a `trigger` event naming `pull`, then each card's `pull` event, then L2's move. #280 relies
on that order.

**Claims on one handle are never released once L2 has moved the card.** No work follows a
claim-only claim, so no slot frees. That is what makes two concurrent calls on one handle claim a
single card exactly once, since the second call's claim step sees the first call's claim.
Calls on one handle also never hold more than N between them. A claim whose move the board refuses
is released, as the loop releases one. The call then rejects with an AggregateError, the shape
`pull()` uses. That refusal behaviour and the "never more than N across calls" behaviour are
outside the card's acceptance. Each has its own test.

**Two readings are judgments.** First, only `undefined` means "no claim limit", so `null` is
refused as a limit that is not a positive whole number. Second, the call records the pull
trigger's `trigger` event even though it fires no drain. The card says a claim-only call "is not
a run of the loop", and I read that as covering drain alone.

**Round 2: redos.** After round 1, the PM revised the acceptance: a claim-only call claims redos,
and claiming a redo moves no card. The code already did both, because the shared `start` step
skips L2's move for a redo, as the loop's does. So the three new redo tests passed as soon as
they were written. Two guarded mutations show that they discriminate. The first moves a redo
anyway, and that reddens the no-move test and the no-transition test. The second drops redos from
the claim-only call, and that reddens all three redo tests and the pull-event test.
