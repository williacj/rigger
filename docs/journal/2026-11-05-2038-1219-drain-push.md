# Stream pushes while run stays up

The owner's ruling after the preflight escalation removes the Table D case prefix from the
held-push poll test and its host-test reference. The PR maps that title to Table D's poll row.
The generated matrix's legacy-title collision is a separate tool fix; this card leaves that
tool and those titles untouched, and reports its remaining preflight failure until told to
merge the fix from main.

Card #1219, acceptance revision e5c9962bdbae, places the drain step in L3 by injection from the
claiming verb. The trigger invokes that step only after its drain event was recorded. A single
pull supplies no step, and a run supplies it only while a clock trigger keeps the run up.

Each push closure holds one active copy and one waiting request. Drains replace a waiting drain;
a return replaces that follow-up, waits for the active copy, then makes its own copy. The file is
read when the request starts. A drain's unsuccessful result is handed to the verb as `{ push }`;
the verb uses L5's exported line composer and its own writer without changing its accumulated
status. A refused event instead takes the existing `{ failure }` route.

## Cases met under D20

- A return arriving after a follow-up has already started waits for that second copy and makes
  a third. This is D8, rather than D9's replacement of a request still waiting in the queue.
- An injected drain step can reject, or throw synchronously. L3 observes either failure and
  hands it to the verb as `{ failure }`, outside the run's work-failure accumulator.
- A throwing verb skips its return push. `recording` still runs its `finally` and ends the sink.
  Ending an already named sink flushes it but does not revoke later appends to that named
  stream. The controlled in-flight copy therefore settles and appends its `push.end` even
  after that `finally`; no return copy is added. The D20 test observes both the sink's end and
  the subsequent append. In the actual bin, `src/cli/rigger.mjs` awaits the verb at top level
  without a catch. Its unhandled rejection ends Node, so L0's registered exit cleanup contains
  the active git group synchronously; there is no return push or wait for the network. D20's
  in-process test catches the rejection so it can inspect the already named sink afterwards.
  A real signal also takes L0's exit cleanup and exits without a subsequent `push.end`, as D17
  checks.

There were no other cases encountered beyond Table D and these cases. The change leaves
`src/cli/recording.mjs` untouched. It adds only test lines, regenerates the test matrix, and
leaves review and merge to the coordinator's judges.

## Hook PID publication

The first host `proof:diff` at local head 107a17095890cfd88f9e54c202bd8ab0299450f1 failed
D17 before SIGTERM: `the receive hook is in flight before the signal`, actual ps status 1,
expected 0. That run did not capture the readiness bytes, so its exact PID argument is unknown.
The owner's next instruction assigns diagnosis of this new test to its maker.

The one hypothesis tested was incomplete PID publication. The shell opens `waiting` for append
before `printf` writes its line; the test's existence check admits that empty intermediate
state. Ten instrumented standalone runs passed with complete lines. A guarded, controlled
counterexample pre-created the empty file, without changing production code, and reproduced
`readiness=""`, `hookPid=0`, ps status 1, and the same named assertion. The mutation receipt
reported killed, original/mutant/restored counts 1/1/1, child exits 0/1/0, and byte-exact clean
restoration. This establishes the fixture defect and a legal ordering that explains the
observed failure; it does not invent the missing bytes from the original run.

The hook now publishes a separate marker after writing its PID line. D17 waits for that marker,
asserts both positive PIDs form one complete line, and records the line and ps answer on every
run. Its fixture starts with the empty file, so mere existence cannot satisfy readiness.
No sleep, retry, timeout increase or relaxed cleanup assertion was added. This change stays
within this card's new test lines. Final-head repeated runs, proof reports, load measurements
and the retained failure are quoted in the PR.
