# #489: the real `gh` in the live judge's shell

**What the re-run showed.** In the owner's re-run at `c63a27a` (issuecomment-5985128002 on #489),
the judge's `gh auth status` reported the owner's real github.com account. The fake forge models no
`auth`, so the real `gh` answered. The test hands L1 a `PATH` with the fake forge's directory
first (`test/provider-codex-live.test.mjs:318`), and that order did not hold in the session's shell.
The round-3 reviewer raised it as B1 on #583.

**The cause, measured on the owner's host with `/bin/zsh`, no agent CLI run.** Both of the routes
below put `/opt/homebrew/bin/gh` ahead of the fake:
- A login `zsh` sources `/etc/zprofile`, which runs `/usr/libexec/path_helper`. That puts
  `/etc/paths` and `/etc/paths.d/*` first, and `/etc/paths.d/homebrew` names `/opt/homebrew/bin`.
  Every directory the caller put first moves after those.
  - `env PATH=<fake>:/usr/bin:/bin /bin/zsh -c 'command -v gh'` gave the fake.
  - The same with `-lc` gave `/opt/homebrew/bin/gh`, and its `PATH` ended with the fake.
  - The owner's `HOME` played no part: an empty `HOME` gave the same answer.
- Codex 0.159.2 has an `allow_login_shell` key: its binary carries "login shell is disabled by
  config; omit `login` or set it to false." It also has a `shell_snapshot` feature. The owner's own
  `~/.codex/shell_snapshots/*.sh` files hold `setopt login` and `export -T PATH path=( … )`,
  captured with `/opt/homebrew/bin` ahead of every directory the caller added.

Which of the two acted in the run is not measured, and both lead to the same order. The fix has to
close both, so its proof is the live run quoting `command -v gh` from the judge's own shell.

**Not production's concern.** Nothing in `src/` relies on the order of a session's `PATH`. A
production judge posts through the real `gh` by design (`R-SAFE-1`, `R-SAFE-2`). The fix belongs
to the live test's world, and its lines wait on a grant on #489.

**What the module now records.** `src/substrate/providers/codex.mjs` had three comments saying a
fact was "not yet measured". They now record what the re-run measured:
- the probe's list agreed with `host_skills` under one home;
- the credential link held, and no token value was in the home.

They also record that no token refresh happened, so a refresh through the link is still
unobserved.
