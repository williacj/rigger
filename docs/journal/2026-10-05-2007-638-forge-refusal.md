ABOUTME: Why card 638 records the forge ruleset as this repository's main-line boundary.

# The forge refuses a push to the main line

The owner chose a forge ruleset under O96 because the session's editing and command permissions
let it run code it wrote. A client hook can warn early, but the session can change its own local
path to the remote. D23 records the boundary where that code cannot run.

The probe used the same ruleset object as `main`. On 2026-10-06, read-only `gh api` calls to the
ruleset and the effective branch rules showed that `main` and `o96-probe/c638` received the same
four rules while the probe pattern was present. The owner changed the ruleset conditions; the
maker never wrote repository settings.

The maker then used a throwaway clone and the owner's credential to try the Git, REST, and
GraphQL updates listed on card #638. The forge refused each one, including a genuine
non-fast-forward force-push and the administrator merge while checks were pending. The branch
SHA was unchanged after each refusal. Once `check (20)` and `check (24)` passed, an ordinary
pull request merge succeeded. The full responses and SHA reads are on card #638.

The owner removed the probe pattern while retaining the explicit `refs/heads/main` condition.
A read-only `gh api` ruleset read at 2026-10-06T01:07:06Z showed the two final conditions, the
four rules, no bypass actor, and `current_user_can_bypass: never`. A guarded `gh api` deletion
then removed the probe ref, and a GET returned 404. The explicit `main` condition keeps that ref
covered if the repository's default branch changes.

The limit remains the shared credential. A ruleset can refuse an update, but it cannot identify
whether the owner's token is used by the owner or by a session. A token able to change settings
can change the rule itself. D23 names the events that would reverse this choice.
