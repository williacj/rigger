ABOUTME: Records why a fired process-table read deadline must outrank an exit-0 partial answer and how the directory wait uses it.

# Card #614: keep a read deadline after the child exits

Node 26.5.0 can call `execFile` back with no error when its child exited 0 but a descendant kept standard output open until Node's timeout killed the child. The output it returns may be empty, complete, or cut. A census can then treat that output as a completed process-table read. The new held-output fixture makes this condition without a sleep; focused tests over base `78554e7` failed on cut rows, an incomplete directory listing, a start-time read, and written standard error.

`run` now owns a timer and records whether it fired. The timer kills the read and rejects with `ETIMEDOUT`; a later callback cannot accept Node's partial output. The deadline takes precedence over output and standard error. Reads that complete before it retain the earlier exit and error handling.

A further test held the descendant's output open while awaiting the call. The first timer change left that call waiting for the descendant, so the new test hit its 20-second test bound. `run` now rejects at the fired deadline and closes its read pipes; the same focused test settles while the holder is still alive, and teardown then ends it.

The directory wait had a separate consequence. Its `reaped` generator treated `LATE` as the bound ending a read, while an `ETIMEDOUT` read fell through to the longer unread-table branch. It now takes the same result from either deadline code: the last read that found a process alive, or an unread-table result if none answered. Focused base tests for both async and exit-cleanup drivers failed on the old reason and passed with this change. The `spawnSync` paths stay unchanged; held-output controls force their timeout behavior.

The PM ruled that the cut-name cases whose public result was already correct at the base are controls, as are the synchronous forcings. This matters because `contain` and `settled` can exhaust their reading deadline in a later read after receiving a partial name, yielding the same final unnamed record. Their tests protect that public result without claiming a red result at the base.

The first full head suite exposed a fixture fault: the `beforeKill` stand-in could enter its cut-read branch repeatedly, starting more than one output holder while the helper remembered only the last PID. The suite completed only after I ended the earlier holder by the PID its fixture had recorded. The helper now records every holder PID for teardown, the stand-in cuts one read, and the new file's tests carry the repository's 20-second test bound. A focused run of that file then passed all seven tests; the same head tests over base source failed on the six behavior-changing cases and passed the `startOf` control. The final local suite passed 2,434 tests with 16 skips.

The recorded-group leader test at base `78554e7` can reach the same path. A forcing printed its leaderless table, exited 0, and kept the pipe open through the deadline. At the base it failed as "left out its leader"; at the local fix it failed as a timed-out read. Neither result authorized the recorded kill.
