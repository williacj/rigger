Every row of #1301's Table T held at the merge base `52fb8a3d`. No adapter changed. The work
was tests that claim `R-SAFE-8` and `R-SAFE-9`.

The live runs were measured on the laptop on 2026-11-08, with Claude Code 2.1.319 and
codex-cli 0.166.0.

| Row | Outcome | At the merge base |
|---|---|---|

**Row T2.** A whole-tool `permissions.deny` rule, `WebFetch`, removed the tool from `init.tools`.
The rule came from the directory's own settings, which the invocation carries across in
`--settings`. The tool was not listed and then refused on call. The session said it had no such
tool, and made no call.

**Row T8.** Codex does give a repository a key that withholds a built-in. `codex features list`
at 0.166.0 shows `sleep_tool` as `stable` and `true`. With `[features]` `sleep_tool = false` in the
declaration, the `clock` namespace and its `sleep` tool were gone from the rollout's
`additional_tools`. `functions.exec` was still offered. The same list shows `shell_tool`,
`view_image`, `image_generation` and `multi_agent` as stable features a declaration could turn
off. Only `sleep_tool` was measured.

**Row T12.** The Codex adapter passes `--disable plugins`, `--disable apps` and `--disable` for
each `HOST_FEATURES` entry on every invocation, whatever the directory declares. So a repository
that declares a plugin, an app or one of those features still gets none of them. The architect
ruled this out of scope on #1301, because `R-SAFE-7` and `R-SAFE-9` only cap use. Whether a
declared tool must be offered would be a new requirement.

**Where the record shows Codex's apps and plugins.** The apps and plugins never appear in the
rollout's `additional_tools`. Apps load as deferred tools, which only the code-mode `exec` tool's
`ALL_TOOLS` lists. So the live cells ask the session to print `ALL_TOOLS` through `exec`, and read
what it printed from the rollout's `custom_tool_call_output`.

The controls showed the source of each tool:

| Control | What it showed |
|---|---|
| without `--disable apps` | `mcp__codex_apps__*` tools for the owner's ChatGPT apps, Gmail, GitHub and Google Calendar among them |
| without `--disable plugins` too | the above, plus `request_plugin_install` |
| without `--disable plugins` too | remote plugins installed into the session's own home under `plugins/cache/openai-curated-remote/` |
| the adapter's own flags | none of these |

**The session's home `config.toml`.** At the start of the session it equals the directory's
declaration. During the run, codex-cli 0.166.0 appends a table that marks the working directory
trusted:

```
[projects."<directory>"]
trust_level = "trusted"
```

So the live cells compare the home's `config.toml` before the session starts. The directory then
being trusted means Codex may also read its own `.codex/config.toml`, which is the same file. Not
followed further here.
