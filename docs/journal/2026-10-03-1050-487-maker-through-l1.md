# #487 — the maker through L1, and the loop world on stand-in processes

**A grant table read line by line still misses the lines a harness reaches only at run time.**
The refreshed table named every line that mentioned the injected dispatch. It missed nine lines.
The first kind was a `decide` that calls `nextAction` with no `roles`. In the loop world, the
retry world, the mid-dispatch engine and the report run, L2's maker answer then names no
provider, and every maker rejects `NOT_STARTED` before a process starts. A facts-pull test also
handed its own loop a no-op sink, so the world's `started` could never record its card. Two
loop tests asserted a cross-card move order that the stand-ins make a race. A third expected a
fulfilled outcome where L1 must reject, because the sink refuses `dispatch.end`. The coordinator
granted all nine under O79
(https://github.com/williacj/rigger/issues/487#issuecomment-5970690296).

**A maker that fails at once reorders the board.** At the base, a card whose answer was an Error
held like any other until the test released it. Now it never starts, so its slot frees at once,
and the next card is claimed and moved to coding before the held card's release. Two makers
released together then exit in whichever order their processes end. The two tests that compared
whole move lists now compare each card's moves in order, and `started`.

**A settling wait has to look a turn after the pull is fired.** A pull records its trigger in
the microtasks after `pull()` returns. Read at once, the world's invariant holds trivially, with
no claim and no trigger pending, so `settling` waits one turn before its first look.

**A wait on the event loop is starved, not bounded, by a loop that never yields.** The first
version of the world marked a card returned only at L1's `dispatch.end`. A maker whose
workspace could not be made never reaches L1, so its card was never fresh. The run re-claimed
it, and kept re-claiming it, in microtasks alone. No `setImmediate` ran again, so no time bound
could fire, and the file hung until it was killed. The world now marks a card returned as L3
hands L2 its outcome, as the base did in its `finally`.

**A stand-in that reads its input before it acts deadlocks a held start read.** In
`restart-kill`, the `ps` stand-in holds L0's start-time read until the command marks `ready`. L0
writes the dispatch's input only after that read, so a stand-in that read all of its input
before exec'ing the shell never reached the shell. A plan under the card `*` now execs before
it reads, which keeps the shell the group's leader.

The measured basis of the 10,000 ms bound, and the re-measured premises of `DRIVEN_ROUNDS` and
`ROUNDS`, are in the pull request, with host, date and loads.
