ABOUTME: Records the evidence and layer choices for #768's waits on forge reads after a write.

# Forge reads after a write (#768)

P58 records two departures in #664's exit run: the lane dropped an unknown mergeability answer
after a preceding merge moved `main`, and a continuing maker's settle judged at the head the forge
still showed before its push appeared. The event stream did not record enough of either read to
distinguish forge lag from another cause by measurement.

The lower bounds in #664's journal and P58 are times when the old fact still appeared: about 2,
2.4, 6 and 7 seconds after writes. The upper bounds in #664's event stream are later invocations
that saw the new facts, 103.5 and 91.7 seconds after the preceding events. Those observations bound
when the invocations saw the facts, not the forge's lag; no run measured that lag. The 5 second
pause and 60 second stop in #768 are judgments from this evidence.

The architect's ruling on #768 places each decision about a read in L2, the repeated request and
clock in L3, the local tip read in L1 through L0, and the forge observations in L0. A lane repeat
is the full board and facts read followed by L2's rule, so it can also catch a changed head, marker
or check. A continuing settle compares the forge's head with the workspace line's local tip before
the move to review and judge selection.

The first regression test made the lane's first read unknown after the pull had already answered
merge. At the baseline implementation it recorded no merge call, even though the fake forge served
mergeable on the next read. This was the missing behavior the lane change started from.

The gate workflow comment also described the wrong scheduling behavior. P58 and #664's journal
record 28 cancelled runs among the fixture's 60 gate events: a new run cancels one still pending
in the same concurrency group. The last run still starts after the last event. The workflow and
its template now state both facts at their shared comment.

The lane's event records the last L2 reason on an unmerged result and the read count and elapsed
time when it read again. A continuing settle uses the workspace branch tip read through L1 and L0
as its expected head; each repeated L2 read either reaches that head or keeps the card in coding.
Its transition or hold event records the forge head it last saw. These fields will let a later
incident distinguish a stale forge read from a maker that left a different local tip.

A second regression test made the forge show the old head once, then close the pull request before
the next read. The hold event initially dropped the prior head and the read count. L2 now carries
that last observed head and the wait measure into the hold when the next read finds no unique open
pull request.
