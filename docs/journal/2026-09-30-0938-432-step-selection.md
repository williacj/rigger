# #432 — L2 selects a card's steps, and L1 runs one

## What we learned

**Rule 9 decides where the step runner can live.** `test/layer-boundaries.mjs` refuses any module
outside `src/scheduling/` that binds L1's `dispatch`, `src/execution/` included. A step runner that
called `dispatch` itself would need its own module to import it, and would break rule 9. It could
instead sit inside `run.mjs` as a second export, but that export would be a dispatching function
rule 9 does not hold. So the runner, `stepDispatch`, only composes what `dispatch` is handed. L3
still makes the one call. The work that has to happen at dispatch time moved into `dispatch`,
under a new `workspace` parameter: naming the workspace, stripping the redirecting variables, and
refusing a `cwd` outside the workspace. A7 already asks for that parameter, because its
environment rule binds every dispatch L1 runs in a workspace, not only a step.

**The containment check belongs after `dispatch.start`, not before it.** Checked in the runner, a
`cwd` that links out of the workspace would reject with no L1 start and no end. L3's start event
(M3-07a) would then have no L1 dispatch to pair with. Checked inside `dispatch`, beside the record's
writability, it is one more way a command never starts, so it gets the same one start and one end
as the others.

**Only the newest outcome's failure is recorded.** L3 asks `nextAction` again after each outcome,
handing it every outcome of the attempt so far. So an optional failure is seen once per later
call. Recording on every call would record it once per later step. `nextAction` records the
failure only when it is the last outcome handed, which is the call that follows it. That rests on
M3-07a's item that L3 asks once per outcome. A caller that asked twice for one outcome would
record it twice.

**Three of the answers are M3-06's to pin, and the rest are left to M3-07.** `stop` is what a
required step's failure answers here. M3-07b turns a first attempt's stop into an attempt again,
with its own event, and does not need to change these tests to do it. An outcome that is neither
L1's result nor a command that never started, such as a refused event, answers no action and
records nothing. That is the halt, and M3-07a's refused-end items test it through `loop`.

**Most L1 items were already true of M2's `dispatch`.** Exit 7, the timeout's kill, and the
survivor kill each passed on first run, because `dispatch` already had those behaviours. So did
the order and label items once selection existed. Guarded mutations showed each such test
discriminates. The pull request records them.
