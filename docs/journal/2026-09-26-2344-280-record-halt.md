# 2026-09-26 — L3 starts no work while the record refuses an event

The halt is three lines of behaviour in `src/scheduling/loop.mjs`, where `ARCHITECTURE.md`,
"Failure model", places it. A pull event the sink refuses releases the claim step 1 took,
records nothing for it, and fails naming the card not started and the sink's error. Nothing
remembers the refusal: the next start tries its own record, and the halt lifts there. The
tests drive the real loop and claim-only call over the fake board with the shared sink
refusing, then accepting, and no event of any kind records a change of admission across the
two calls.

**A trigger's refusal is carried, not fatal.** At the base, a sink refusing every append made
the claim-only call reject on its first append, the pull trigger's event, before the board was
read, so its failure named no card. The acceptance asks for the card not started, and only a
start's own record names one. So `take` keeps the trigger refusal beside the claims it answers,
the pull goes on to try each start's record, and every refusal is reported together. A trigger
is no start, and `ARCHITECTURE.md`, "Telemetry", has no layer drop a refused append, so
carrying it is the reading that keeps both. A refused `run.start` still rejects the run before
its first pull, as it did at the base; the halt's items hold either way, and nothing asked for
more.

**A release records nothing for a claim already released.** `release` used to record a
`slot.release` event whether or not the claim was held. After a refused pull, that event would
be the orphan the Codex reviewer on PR #313 traced to a `NaN` utilization in `report`: a
release with no pull before it. `release` now records only where it found the claim, so no
release event lacks its pull, and the production path to that `NaN` is gone. `report` itself is
untouched, because no item here covers it; the orphan-release test in `test/loop.test.mjs`
refuses exactly the trigger and pull appends and shows the stream never written.

**Neither failure hides the other.** The reviewer on PR #306 saw a refused `slot.release` mask
the pull refusal before it, and skip `freed()`. `released` in `loop.mjs` now releases the slot
after whatever ended a card's work and answers both failures in one AggregateError where there
are two, and `work` runs `freed()` after the release whichever way the release went. L2's
report of a refused transition passes through this unchanged: the item 9 test finds the exact
message L2 threw among the opened failures, with the sink's error as its cause.

**The verbs print what L3 reported.** `claimVerb` in `src/cli/once.mjs` used to let a failure
escape, and the bin printed a stack dump. It now opens the AggregateErrors L3 nests and prints
one `rigger <verb>: ` line per failure, then exits 1. The card places this in `verbs.mjs`, but
#233 moved the shared body into `once.mjs`, so that is where the output lives.

**The real bin, with the record refusing.** A stream that is a directory refuses every append
with `EISDIR`, whoever runs the test, so the from-the-start cases make `.rigger/events.jsonl` a
directory before the run. The after-the-move cases need the sink to accept L3's events and
refuse L2's, from outside the process: `installGhRefusingStreamAfterMove` in `test/fake-gh.mjs`
is a `gh` placed ahead of the fake that answers as it does and makes the stream that directory
once it has answered the move mutation. Every such test has the fake `gh` first on PATH, ahead
of the refusing one `npm test` puts there.

**Seven guarded mutations** (`c280-mutate.mjs` and `c280-mutations.mjs` in the session
scratchpad, logs `c280-mutation-*.log`), each with one anchor, read back off disk, run to a
verdict on its target and restored with `git status` clean. The halt removed reddens eight
loop tests, the no-claim and empty-write-record tests among them; the pull event moved after
the claim move reddens three, the one-sequence test among them; the outcome held back from L2
reddens five; a latch added to the halt reddens seven, the lifting test among them; the release
refusal masking the failure before it reddens the item 9 test alone; a release recorded for a
claim already released reddens two, the orphan-release test among them; and the verb letting

**Round 2: a redo made the run spin.** The reviewer measured, on a fresh clone at the first
head, a run over one redo card with the sink refusing from the first read on: thirteen board
reads, the same two failures twelve times, and no end without a guard. `work` counted a redo as
started before its start was made, so a refused pull event still fired the next trigger at once,
which claimed the same redo again. The owner's ruling on #228 has a refused start wait for the
next trigger, and this card's own `work` contract said so of the sink. The start is now made,
for a redo as for a Ready card, only once `start` returns. The test drives a redo through
`run()` under that sink and shows one board read, with the second read throwing so that a run
that did spin still ends and reports; restoring the spin reddens it alone. A second test pins the
carried trigger refusal beside the start not made, which the reviewer found untested; dropping
the refusal reddens it alone.
