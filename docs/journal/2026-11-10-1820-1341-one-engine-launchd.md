ABOUTME: Records what launchd did with the shipped LaunchAgent under test labels, for R-WORK-4 (#1341).

Card #1341 claims `R-WORK-4` through the shipped template, as M8-U2 Q12 a rules. The new tests
in `test/launchd-host.test.mjs` render `templates/launchd/com.williacj.rigger.plist` under a label
`com.williacj.rigger.test-<pid>-<n>`, and load it into `gui/501` with `/bin/launchctl`. They run
only with `RIGGER_LIVE_LAUNCHD=1`. The job's program is a node stand-in. It appends each start and
exit, with its pid and `Date.now()`, to one record, and it holds on a FIFO until the test
releases it.

Every figure below is a measurement: the stand-in's own record, as the test's diagnostics
printed it. The run was `sh test/suite.sh --host test/launchd-host.test.mjs` through the suite
slot, with `RIGGER_LIVE_LAUNCHD=1`, on the laptop: macOS 27.2 (26B123), arm64, node 26, user
`cjwilliams`, uid 501. It ran on 2026-11-10 at merge `c19377ec`, with the counterpart-comment
edit later committed as `db4bc7b6`. The test file's pid was 36683. `StartInterval` was 5 s in
every row, and `ExitTimeOut` was 5 s.

|---|---|---|---|---|---|
| L1 | `…test-36683-1` | 36695, 2026-11-10T18:20:15.686Z | none: held 16,097 ms, then booted out | none while held | not applicable |

| L3 (one instance) | `…test-36683-5` | 37349, 18:21:15.525Z | none: booted out | none within the 10 s wait | not applicable |

In both L3 rows, the second `bootstrap gui/501 <plist>` of the loaded label exited 5. Its
message was "Bootstrap failed: 5: Input/output error".

L1 held its instance across three `StartInterval` periods and saw one start. launchd missed
the firings at about 5, 10 and 15 s rather than queueing them. After the release, the next
start came about 5.1 s after the exit in both L2 runs. That delay is within one
`StartInterval`, and well inside the card's bound of `StartInterval` plus 10 s. That is the
missed-firing behaviour `launchd.plist(5)` documents. The phase of the 5 s timer after the exit
was not measured separately. A delay of about one interval is consistent with the timer
restarting at the exit, but these runs do not settle whether it does.

The stale-label sweep found none: every test printed "stale test labels: none". After each
test, `print gui/501/<label>` answered that the label was not loaded.

The mutation runs loaded two plists that differed only in `Label`, `…-<pid>-1` and `…-<pid>-2`,
whose stand-ins wrote one record. Each turned its target test red on the assertion it names:

- L1: "exactly one start while the first instance runs";
- L2 order: "the second start … is no earlier than the first instance's exit";
- L3 refused: "a second bootstrap of the loaded label exits non-zero";
- L3 one instance: "one start after the refused bootstrap".

The first L1 mutation failed on the hold-length assertion instead, because a second start ends
the hold early. The start count is now asserted first.
