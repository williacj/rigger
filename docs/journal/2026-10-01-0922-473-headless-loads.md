# #473 — what headless sessions load, and what keeps it out

**The flag the ruling named for Codex defeats the purpose it was named for.** `--ignore-user-config`
drops the trust entry that Codex needs before it reads a repository's own `.codex/config.toml`. So
under it the project's servers and instructions never arrive. A per-dispatch Codex home holding the
declaration as its own `config.toml` carried it, and so did `-c` overrides. Reasoning from the help
text would not have found this. The help says only "Do not load `$CODEX_HOME/config.toml`".

**Claude Code's two flags held most of the user's configuration out, but not the neighbours.** A
parent `CLAUDE.md`, auto-memory shared across worktrees, bundled skills, two built-in plugins and
the worktree tool all reached a session under both. Each had a withholder, and one,
`CLAUDE_CODE_DISABLE_BUNDLED_SKILLS`, appears in no help text.

**Some sources have no printed record, and the evidence had to come from somewhere else.**
Claude Code's `init` event lists what it loaded. Codex's `--json` lists nothing, so the evidence came
from four other places:

- the rollout file;
- `codex debug prompt-input`;
- an MCP server that logs its own start;
- for the user's `CLAUDE.md`, a local stand-in for the Messages API that recorded the request body.

The stand-in kept the owner's `~/.claude/` unedited while other sessions shared the host.

**The harness bug cost two runs, and shows why a check needs a control.** My runner stripped every
`CLAUDE*` variable, including the ones a run set on purpose. Both variables then looked inert.
Narrowing the strip to the inherited names reversed both findings. A variable under test needs a
run showing it reached the process.

**One item stays open.** No Codex token refresh happened during the runs, and I would not force one
by editing the owner's credentials. The report says what run would settle it.
