# 2026-09-28 — The kill path asks the leader's pid

**A live leader every read hid was killed unrecorded.** The census, `killedOf` and `outlived` asked
signal 0 of the group, and of a pid only once the census had named it. So a `ps` that exited 0 and
listed only the group's zombies while the leader lived gave the census no survivors, gave
`outlived` nothing live, and the group's kill ended the leader with no event. The new test in
`test/process-adapter.test.mjs` shows it at the base: the call recorded `[]`.

**The census now does what `startsIn` does.** The group's id is the leader's pid, so where reads
that agree leave out the leader while that pid still answers signal 0, the census reads again, and
at its timeout fails naming the leader, so the group's kill is recorded. A leader that has exited
and not been reaped is listed as a zombie, and one that has been reaped no longer answers, so
neither holds the census. The check is in the census alone: a leader the census names is held by
`killedOf`'s own check of a named pid, so no later read can hide it unrecorded.

**Both notes now record one class.** Beside `outlived` and `startsIn`, the excluded class is a read
that exits 0, lists at least one row, and consistently leaves out a live member other than the
leader. Each note says why an empty read is outside it on its own path: the kill path retries it
and records the group's kill, and the start path retries it and fails killing nothing. The
`startsIn` note had counted an empty read inside its class; the card's revised "Lands in" asked
for that correction.

**What the leader check costs.** A leader alive but outside its group would hold the census to its
timeout and have the group killed unnamed. The adapter spawns each command `detached`, which on
POSIX makes it a session leader, and a session leader cannot change its group, so that is a
judgment from `setpgid`'s rules, not a measurement.
