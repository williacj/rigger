# 2026-09-27 — L0's process adapter kills and records a command's survivors

**The fixtures had to wait for their own children.** A fixture that ignores `SIGTERM` passed a
mutant that sent `SIGTERM` instead of `SIGKILL`. The command had exited, and been followed by the
kill, before its child ran `trap '' TERM`, so the child died of a signal it would have ignored a
moment later. The command now waits for a file the child writes once it ignores the signal, and
the same mutant hangs that test. Any fixture whose property is set after the fork needs that
handshake.

**macOS answers `EPERM` while a killed group empties.** Polling `kill(-group, 0)` after a
`SIGKILL` answered `EPERM` once in each of 200 groups before `ESRCH` (Node 26.5.0, macOS 27.0), so
the adapter reads `EPERM` as a member left and keeps waiting. The first build threw on it, and
only some runs hit it.

**`ps` under no locale is not `ps` under the caller's.** The repository's own sweep requires a
spawn to name its environment. `ps` given an empty one writes non-ASCII in `vis` form (`ü` as
`M-CM-<`), so it gets `LC_ALL=C.UTF-8` and nothing else. With no `PATH` in that environment, Node
also finds a bare `ps` through the system's default path. So the narrow-`PATH` test alone does not
catch `ps` named without its path; the test on `PS` does.

**The engineer's `ps -A` cut did not reproduce.** Round 4 on #332 measured a whole-table read
cutting command lines at about 1,160 characters. Here `ps -A`, `ps -g` and `ps -p` all returned an
argument of 10,031 characters whole, with `COLUMNS` unset, 80 or 1160, and one of 100,000 as
well. The cause is unknown, so the adapter reads one group with `-ww`, and records both
measurements beside the call.

**Teardown finds fixtures by their command line.** Every fixture names its scratch directory in its
arguments, so each test's teardown runs `pkill -f` on that directory whether the test passed,
failed or timed out. After every red run in this work, including the hanging ones, `pgrep` found
none left.

**The judge's round found three things the first head missed.**

- **One group kill is not enough.** A process forked while the kernel delivers the kill can join
  the group without receiving it. So the adapter now sends the kill again on every turn until the
  group is empty. The test has four survivors forking in a loop. It hung 3 of 3 times on one kill,
  and settles every time with the kill resent.
- **Two `ps` runs can describe two images.** The name and the command line were read in two runs,
  and a process that re-executed between them was named by one image and described by the other.
  One row cannot hold argv[0] and the command line both whole. So the name is now the
  executable's (`ucomm`), read in the same row. A `ps` stand-in that re-executes the survivor
  between reads shows the mixed pair on the old census every time. On macOS a script run by
  `/bin/sh` is named `bash`, the executable that actually runs, so that test names `/bin/bash`.
- **Two fixtures raced their own children.** A fixture's `&` returns before the child execs, so a
  census could name the forking shell. The fixture now waits until `ps` shows the expected
  executable. The stand-in `ps` could be killed at its 200 ms timeout before it wrote its pid, so
  the test now looks for it by command line.

**Round 2 showed that one `ps` run is two reads.** `ps` takes the name from the process table and
reads the arguments a moment later, so a process that execs in between still gets a mixed record.
The engineer judge measured this in 34 of 1,500 calls. Now the census stops the group, and it
records only from a read in which every member shows as stopped: a stopped process cannot exec.
The judge's 1,500-call experiment then gave 0 mixed pairs. A `ps` stand-in splits one read around
an exec, and it redded the unstopped census every time. A second stand-in resumes the group before
its first read, which reaches the re-read of a member that is not yet stopped.

**Stopping the group changed what the forking test proves.** Once the group is stopped, nothing
forks at the kill, so a single kill was enough and the test no longer caught one (0 of 6). A fork
race can't be made certain anyway: with the group running, 4 forkers caught a single kill 7 of 10
times. The test that catches it every time has a process outside the group join it after the kill.
It does that while its zombie child, which it has not reaped, keeps the group in being. A single
kill then hung 12 of 12 times.

**Round 3 broke the row parser on a wide name.** `ps` pads a column by display width, but the
parser counted characters. So after a name like `日本語日本` it read past the state into the command
line, and could take a dying process for a stopped one. A row also failed to parse when its state
was `?` (mid-exec), and that failed the whole census. Now each read holds the pid and one column:
the states, the names, the command lines, then the states again. The census keeps a read only when
both state reads find every member stopped, and all four reads hold the same processes; anything
else, `?` included, is stopped and read again. Reading the columns separately is safe only because
the group is stopped, so no one of those reads can see a different image from another. The
wide-name test compiles its own `pause()` binary, because the kernel kills a copied system binary
on launch and a symlink runs under its target's name. The judge's 1,500-call experiment gave 0
mixed pairs and 0 unnamed kills.
