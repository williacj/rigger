# 2026-09-24 — The hook exported the branch it was committing, and the fixtures believed it

`docs/journal/2026-09-23-2239-76-the-gate-corrupts-a-linked-worktree.md` established the fault and the arrangement table; this adds the count, the damage the count exposes, and the choice of side. `GIT_TRACE` and `GIT_TRACE_SETUP` over one suite run in a linked worktree of a clean clone at `716f419` logged 101 git invocations, of which **46 resolved the committing worktree's git dir** rather than the fixture's — `add -A`, `commit -qm fixture`, `config user.name`, `remote add`, `remote get-url`, `ls-files` and `show`. The same suite run from the main checkout of the same clone logged 126 invocations and resolved none of them there. The count is what turns a story about one branch into a list of the places to fix, because the argvs it names are the call sites.

A fixture wrote three keys into the shared config, not one. After that run the clone's `.git/config` held `bare = true`, `user.name = fixture` and `user.email = fixture@example.invalid`; the two identity keys trace to one line, `test/ruled-out-word-check.test.mjs`'s `repositoryOf`, and `bare` to `git init -q` running with `GIT_DIR` set and no work tree, which is git's spelling of a bare repository. This checkout's own `.git/config` carries both identity keys today, measured by `git config --show-origin --get user.name` in `C:/Users/williacj/github/rigger`, which answers `file:.git/config fixture`, while commits up to `3762efb` are authored `williacj`. So the fault has been rewriting the identity of every session that shares this repository, and no test could notice, because the suite reads back what it wrote.

A commit from a main checkout really is safe, and not for the recorded reason. Measured twice, on two throwaway repositories, by installing a hook that dumps its own `GIT_*` environment and refuses: a main checkout's hook is handed `GIT_INDEX_FILE=.git/index`, `GIT_PREFIX=`, the author fields and `GIT_EXEC_PATH`, and **no `GIT_DIR` and no `GIT_WORK_TREE` at all** — the `.git` that card #76's entry records is `git rev-parse --git-dir`'s answer, which is git's own view rather than a variable git exported. What makes the arrangement safe is narrower and worth knowing: a relative `GIT_INDEX_FILE` resolves against the top of the working tree git found, not against the directory git was run in. Measured by running `git ls-files --full-name -- :/` under that variable from a fixture's root, from a subdirectory of it, and from a second repository with `-C` naming the fixture, where only the third moved. Every fixture here names a repository root, so every one of them landed on the right index by arithmetic rather than by intent.

That third measurement replaced a hypothesis, and how it failed is the transferable part. The first guess was that a fixture run from a subdirectory would silently read an index that does not exist, and the probe that appeared to confirm it — `git ls-files` from that subdirectory answering nothing — was reading `ls-files`'s own scoping to the current directory and not a wrong index at all. A measurement agreeing with the hypothesis is worth one that discriminates only when the surface it reads is the surface in question.

Three measurements chose the fixtures over the gate, rather than the count of places. First, the damage needs no hook: exporting `GIT_DIR` and `GIT_INDEX_FILE` into a shell and running `npm test` in the linked worktree gave 17 failures, one commit titled `fixture`, the index cut from 126 entries to 1, and `core.bare` flipped — so a gate that scrubbed its own environment would still leave `git bisect run`, `git rebase --exec`, and any shell carrying the variables. Second, the five test files are fourteen call sites: the repository's own tokenizer, run over every `.mjs` under `src/`, `scripts/` and `test/`, finds fourteen calls whose command is the literal `git`, ten of them fixtures and four of them `src/cli/init.mjs`, `src/cli/doctor.mjs`, `scripts/ruled-out-word-check.mjs` and `scripts/absorption-check.mjs` — and a gate in `.githooks/` covers none of the four once the engine runs in a consumer's repository. Third, `.githooks/` is this engine's own live gate, which the owner merges by hand, and the fixtures are not.

The production half was more than a fixture problem, and reading the code would not have found it. `repoSlug` under an inherited `GIT_DIR` reads another repository's remote, and would write a consumer a config naming a repository nobody has. `repoRoot` is worse: `git -C <a-directory-that-is-no-repository> rev-parse --show-toplevel` **succeeds** under an inherited `GIT_DIR` and names that directory, where without it git exits 128 — so the one authority `R-SAFE-5` rests on answers a repository for a directory that is none. That is the shape card #34's entry had already named twice, a total function answering a narrower question than the one it was asked. It surfaced only from writing the test that asserted the relation to git and watching which of the four production entry points moved.
