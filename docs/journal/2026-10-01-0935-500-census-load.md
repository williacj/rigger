ABOUTME: Journal for #500: two zombie-group tests lost the survivor under load because their
`ps` stand-in's first exec, held by the system, was the census's first read.

# #500 — a stand-in's first exec is a read with a timeout

**Both failures had one cause, and it was the test's.** Each test hands the adapter a `ps`
stand-in written moments before, with a `readTimeout` of 1,000 ms. The census's first read of the
group is the stand-in's first exec. The system holds the first exec of a freshly written file
while it assesses it, and `test/process-fixtures.mjs` (`warmed`) records one such hold of 1,058 ms
at a load of about 33. Where that hold outlasts the read's 1,000 ms, `run` kills the stand-in
before it reaches its body. The census then fails, and the adapter records only the group's kill,
`the process-table read timed out after 1000 ms`. The test at `:1386` never sees its census read
cut, and the one at `:1505` sees no `survivor.killed`. Its later reads of the group's states are
the stand-in's second and later execs, so they run, and its `failed` check still passes.

**The forcing held the first exec rather than waiting for load.** A forcing applied to
`fixture` made each `ps` stand-in's first exec stop itself until it was killed, with no timer.
At the base that reproduced both failures 10 runs in 10, and failure A's forced run took the
2,209 ms its load-only failure took (2,210 ms). The adapter's own handling was right throughout:
a census that cannot read the table is meant to record the group's kill unnamed (`R-STATE-12`).

**The fix pays the hold before the call.** Both stand-ins are now `warmed`, as the timeout test's
command already was, so the census's first read is the stand-in's second exec. No bound moved.
The sibling test at `:1498` shares `lastReadFailing` and failed the same way once (PR #499's
Codex round 2), so the same change covers it.
