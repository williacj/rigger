# #538 — one `Monitor`, and why there were two

**The session had nothing to wait on inside its turn.** `Monitor`'s start result says only that
the monitor started. Its event reaches the session as a task notification. In the probe's
transcripts below, on Claude Code 2.1.287, a queued notification reached the model only with its
next tool result, or as a new turn once the current one had ended. The base prompt said "Wait for its event". In most runs the session ended its turn with
"Waiting for the monitor's event." and got the notification as its next turn. In the rest it
made a second call within the turn: the same `Monitor` again, or once a `true` no-op `Monitor`,
as #535's judge saw with `sleep 1`. That second call's result is what delivered the first
notification.

**The transcript shows it.** The live runs pass `--no-session-persistence`, so the stream has no
record of what the model was handed. A throwaway probe, never committed, ran the same session
with persistence on and printed its transcript. In each doubled run the first notification was
enqueued before the second call but reached the model only as an attachment after it. Each
time, the session's own answer said why. In one it said "The first one's start message didn't
show an event, so I started a second." In another it said "The first one's start message gave no
output, so I started it again by mistake."

**The prompt now says how the event arrives.** It says the start result holds no event, that the
event comes once the turn ends, and to end the turn at once with `WAITING`. No assertion moved.
The pull request gives the base and head counts.
