# Set-aside memory

`loop.mjs`'s `run` now holds one memory per invocation, `setAside`, in place of its set of
excluded card numbers. It keeps each set-aside card's compared column and how many reads of the
board had begun when the run set the card aside. Beside it, it counts each card's stops for a line
of work moved or deleted. `take`'s `available` asks it whether a read skips a card.

## Cases met under S12

- **The settle's move to Review.** L2's `settled` answers the facts it read, and those facts go back
  to L2's next action unread, so a field added to them changes what existing tests compare
  (`test/settle.test.mjs`, `test/attempt.test.mjs`). So the settle hands the column the board
  accepted to a `placed` callback L3 passes in its options, and a settle rejected after the board
  accepted its move carries the column as `column` on its rejection, which `attempt` takes from
  `settled.reason`. Round 1 took Review from the settle's facts answer instead and lost the column
  when the settle rejected, which both judges caught (1192#6582825966, 1192#6582575121).
- **A continuing claim's line stop.** A continuing attempt that did not settle is set aside, and
  round 1 applied that rule after the line-stop count, so a continuing claim was set aside at its
  first line stop (1192#6582575121). The stop's line-stop rule now decides for every claim.
- **A continuing claim from Owner stopped once.** Its first stop leaves it in Coding, where L2 does
  not read the owner's marker and answers it no claim, so it is never stopped a second time until a
  person moves it.
- **A change the board accepted, then a later write refused.** The escalation label refused after
  the move to Owner, a move whose transition went unrecorded, and a move the item-write side marked
  made all reject after the board accepted the move. Each rejection carries the column as
  `column`, and L3 takes it wherever the rejection reaches it: `work`'s catch, the settle's
  `settled.reason`, and the lane's `mergeEnded`.
- **A claim whose own move rejects.** A fresh claim whose start rejects is not set aside: it waits
  for the next trigger, as before this card, so it takes no compared column. A continuing claim whose
  start rejects is set aside, by the rule for a continuing attempt that did not settle. Where the
  board accepted its move to Coding before the rejection, Coding is its compared column, taken from
  the rejection's `column`; where the board refused the move, the column the claim read stays its
  compared column. Round 2's account said neither kind was set aside, which the reviewer caught
  (1192#6584461541).
- **Every site a column reaches L3.** The attacker on round 3 found four handoffs no row exercised:
  a made move refused at its event, a made escalation label refused at its event, a merge the lane
  found conflicting, and a removal's following claim. The S5 table now drives every such site in
  `src/` through each outcome it can produce. Two production lines changed so each site has one
  row. The two settles of a maker share one call that hands L2 `placed`, so the continuing tip path,
  which needs a real process, uses the same handoff the table exercises. A successful plain move
  no longer hands its column to the memory, because it sets nothing aside and no rule reads it.
- **One record of the column this run last accepted (M7-K45).** Five rounds each found one more
  path whose accepted column missed the compared column, the last two after #1177 merged: a
  firing's recovery moved a card while its claim still worked it, and creation's delayed `created`
  move landed after a pull had claimed the newly visible card and set it aside (1192#6592601382,
  1192#6592472670). Round 4 had called `clockCardAfter` no site because no claim held the card, and
  round 5 had called `openClockCard` no site because its issue was new; both were wrong. The run
  now keeps one record per card of the column it last accepted for it, or read as it claimed it.
  Every accepted change updates it from any path, claimed, set aside or neither: each claim-path
  site, `created` from `openClockCard` and `clockCardAfter`, and a move whose record was refused.
  A claim takes its read's column only where the run accepted no change since that read began.
  Setting a card aside reads its compared column from the record, and `work` keeps no column.
- **Reads in flight (the architect's ruling on round 6's attacker).** Ordering the record by when a
  read began was wrong both ways. A read that snapshotted the record's column before this run's own
  `created` move landed ended the skip on the run's own write. And a claim that ignored its read's
  column, because a run change landed before the snapshot, kept a column the board no longer
  showed. Now each read in flight keeps, per card, the record's column as it began and the target
  of each run-owned change accepted while it was in flight. A read begun after the setting aside
  ends the skip only at a column outside all of those. A claim takes its read's column
  unconditionally. Only a claim and an accepted run-owned change write the record; a successful
  plain move writes it too, though no rule reads it until the card's next claim overwrites it.
  - **The premise** behind the unconditional claim is that the only run-owned change that reaches an
    unclaimed card is a clock card's `created` placement, and that it reaches only a card in no
    column. What would reverse it: a run-owned change that reaches an unclaimed card already in a
    column.
  - **One consequence, dropped from round 6's first head.** A claiming read snapshots a card in Owner;
    a person removes the card, and recovery places it in Ready before the claim is taken. The claim
    then sets it aside with Owner, and the next read, finding Ready, ends the skip. Round 6's first
    head kept the run's Ready there, and its `S5 claiming read` row asserted that. The ruling takes
    the read's column, and the person's removal is a change the read did not see, so the row is gone.
- **The status issue's notice move** is still no site: L2 answers no action for an item carrying
  the status label, so it is never claimed or set aside.
- **How the tests see a compared column.** L2 answers an escalated card no action, so a claim count
  cannot show whether such a card's skip held. The S5 tests count the reads that hand the card to
  L2's facts call, which a skipped card never is, and a label's removal, which moves nothing, ends
  no skip.
- **When the run sets a card aside.** At the end of its claim's work, just before its release. A
  card's claim is held until then, so no read could claim it earlier, and every read begun before
  that instant is a read begun before the setting aside.
- **When a read begins.** As `take`'s claim starts, before it reads the columns.
- **A merge's end.** `lane.mjs` is not this card's to change. `loop` hands the lane an `l2` whose
  `mergeEnded` keeps the column it answered for that card, and `merged` takes it.
- **A refused routing comment.** The escalation it routes is already set aside by `remember`, so the
  separate exclusion on that path was redundant, and it is gone.
- **Which stop is a line stop.** The stop's own failure decides: an attempt failing `LINE_MOVED` or
  `LINE_DELETED`, even after a first attempt that failed another way.
- **A line stop's count while no skip ends.** It lasts the invocation. A card stopped once, then
  worked without a stop, is remembered at a later second stop in the same invocation.
- **A run with no clock trigger.** The count applies there too, so a drained run claims a line-moved
  card twice, then sets it aside. No skip ends in such a run (S9).
- **A Review card holding nothing, after its skip ends.** L2 does it again from the beginning
  (`R-WORK-24`), so the run dispatches its maker again, as for any Review card holding nothing.
- **Record lines.** The memory writes no event, so no record line L3 writes changed.

## How the deterministic world stands in for a maker
