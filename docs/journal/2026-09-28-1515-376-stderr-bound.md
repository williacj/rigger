# #376 — Exit never spins on an undrained standard error

## What was built

`writeWhole` retried `EAGAIN` at once and without end. A reader that kept standard error open and
stopped draining it held the exit cleanup, or a sink's end, in a busy loop, and the process never
ended. Codex noted it on #353 and on every round of #366.

The write now pauses on a full pipe, synchronously, because there is nothing to wait on at exit. It
gives up once `UNDRAINED_BOUND` (one second) would pass, and drops what it has not written. Once one
write has given up, every later write gives up at the first full pipe. So the process waits on such
a reader once, however many writes the cleanup makes.

Two limits are now recorded beside the code, and neither changes behaviour:

- `OUTPUT_BOUND`: a detached holder's bytes before the bound are in the result, and later ones are
  dropped (the owner's Q6; the engineer's N1 on #361).
- `startOf`: a stalled start-time read blocks the event loop for up to its timeout. The read stays
  synchronous because L1 writes the entry in the step that spawns the group (ruling 1, P2; the
  engineer's N2 on #365).

## What we learned

- **A FIFO makes a reader that never drains.** The test opens its read end without blocking, then
  its write end, and hands the write end to the child as fd 2. The child's `process.stderr` makes
  the descriptor non-blocking, so a full pipe answers `EAGAIN`. A scratch run on 2026-09-28 got
  555,846 refusals in 3 s, with Node 26.5.0 on macOS 27.0.
- **A strict "within the bound" needs time in hand.** The first version began a pause only where
  it would end before the deadline. Locally, the test's end-then-emit case then measured 1,000.35 ms
  in one run, because the last pause woke late and the second write added its own time. Keeping one
  10 ms pause in hand passed three local runs. CI's Node 20 job (run 36478413721) then measured the
  exit cleanup's write at 1,030.7 ms. So the write now keeps `SPARE`, a tenth of the bound, in hand.
- **The bound must run from the reader's last take, not the write's start.** With the bound
  counted from the start and 10 ms pauses, CI's Node 20 job (run 36479120537) cut short the base's
  own test of 200,000 bytes to a live reader, after 980 ms. Node 20's `writeSync` takes 8,192 bytes
  at a time, so the write meets a full pipe many times: a scratch probe with Node 20.20.2 on
  2026-09-28 met it up to 26 times in 240,000 bytes. Each 10 ms pause took about 13 ms locally, and
  longer on CI. The bound now restarts whenever the reader takes bytes, and the pause is 1 ms. The
  local run could not reproduce the cut. The base's test is the one that failed.
- **Stickiness is what bounds the process.** Without the `abandoned` flag, the end-then-emit test
  measured 1,967 ms: each write waited its own bound.
- **An EAGAIN bound is no bound on a blocking descriptor.** Both judges on #387 found that a
  standard error no code had touched is the pipe as inherited, which is blocking. So `writeSync`
  waited in the kernel, and a `SIGTERM` caller or `sink.end()` never returned. The tests had
  touched `process.stderr` first, as the verbs do, so they never met the case. A probe on
  2026-09-28 with Node 20.20.2 and 26.5.0 on macOS 27.0 tried three ways of reaching fd 2 on an
  undrained FIFO:
  - untouched: blocked past 3 s;
  - `process.stderr` opened first: refused with EAGAIN;
  - `/dev/fd/2` reopened `O_NONBLOCK`: blocked past 3 s, because on macOS that shares the inherited
    file.

  So `writeWhole` opens `process.stderr` before it writes, and every bounded test now runs with
  standard error touched and untouched. How Node leaves a pipe on Linux is not measured here.
- **The give-up clears when the reader takes bytes.** The engineer judge on #387 (N33) saw a
  reader that drained again get 8,192 of 200,000 bytes of a later write. That write gave up at its
  first full pipe. A write the reader takes bytes of now clears it. The test that shows this raced
  once in eight runs, when the child's write found the pipe still full because the test had not
  yet read. The test now says `draining` only after its first read, and the comment states the
  limit: a reader that has begun draining but not yet made room loses that write.
