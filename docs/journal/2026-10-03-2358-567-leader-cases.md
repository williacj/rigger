# #567 — the leader's wait status, a leader recorded as killed, and a late member named

**What a leader's zombie hides.** Node reaps no child while the exit cleanup runs, so a killed
leader stays a zombie in its group, and signal 0 reaches it as it reaches a live one. Once the
process table stops answering after the kill, nothing L0 reads tells the leader the kill ended from
one it did not. A leader that answers `EPERM` is the exception: its zombie would not. So that half
of O5 is held here, and the half for a leader the kill does not end went to the architect. Any
answer to that half also changes what `test/exit-cleanup.test.mjs:1123` asserts of a leader the
kill did end, and the grant withheld that line.

**A late member can be named.** A process that joins the group after the read before the kill, and
outlives the kill, is now named by the confirmation that first finds it. On the Linux cloud
container, the two reads that name it took at most 46.66 ms over 200 runs, against the cleanup's
own bound of 1,000 ms (`c567-o6-measure.log` in the session's scratchpad).

**A member every read hides cannot be recorded.** No read and no signal tells a table that hides a
live member from one that does not. Signal 0 to the group answers for a zombie as for a live
member, and at the exit cleanup the leader's zombie always answers. `beforeKill` already records
that limit under `D16` rule 3. The hidden-member item is escalated as `ambiguous`, naming
`R-STATE-12`.

**How these ran here.** This container's pid 1 never reaps orphans, and its `ps` prints `xstat` as
`-`. So the targeted runs ran under a subreaper, host tooling kept in the session's scratchpad,
never the repository's. The suite's evidence is macOS CI.
