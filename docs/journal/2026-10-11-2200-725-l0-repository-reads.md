# Four repository reads for the gate script

Card #725 adds `readDefaultBranch`, `readIssue`, `readPullRequestByNumber` and `readFileAt` to
`repositoryReads`, so #702's gate script can read the forge through L0 alone. Each is one GraphQL
query sent through the read runner.

## What gh answered

The maker captured each read's answer with gh 2.99.0 on 2026-10-11, read-only, outside `npm test`.
The captures are under `test/fixtures/`, dated in their names. Four findings shaped the code:

- **Not found is an exit of 1 with the whole response on stdout.** For an issue number that names a
  pull request, or nothing, gh exits 1. It prints `{"data":{"repository":{"issue":null}},"errors":[{"type":"NOT_FOUND","path":["repository","issue"],…}]}`
  on stdout and the message on stderr. A file path the commit does not hold answers the same way,
  at `repository.object.file`, with the commit's `oid` still in the data. So `readIssue` answers
  null, and `readFileAt` answers null, only where every error is `NOT_FOUND` at that read's own path
  and the field there is null. Any other failure rejects.
- **A missing commit is not a missing file.** `object(oid:)` for a commit the repository does not
  hold answers `object: null` with exit 0. For a tree's oid it answers `object: {}`, because no
  fragment matches. `readFileAt` answers null only where the answer shows the commit asked for.
- **GitHub answers a link's target as its text.** git/git's `RelNotes` is a link, mode 120000.
  GitHub answers it as a blob whose text is the target's path. A submodule answers mode 160000,
  type `commit` and no object. So `readFileAt` accepts only modes 100644 and 100755 of type `blob`.
- **A large text file is sent truncated, not empty.** git/git's `po/bg.po`, 1,088,754 bytes, came
  back `isTruncated: true` with 385,073 characters of text. `readFileAt` rejects any blob that is
  flagged truncated, has no text, or whose text is not its byte size in UTF-8. A file whose bytes
  are not UTF-8 therefore rejects too.

Three rows could not be captured, because no example was at hand: a repository with no default
branch, a pull request whose head repository was deleted, and an issue transferred out. Each test's comment names the GitHub
documentation page its constructed answer follows.

## Labels: the issue read pages, the item read refuses

`readItems` refuses a card with more than one page of labels (`read.mjs`, `cardOf`). Its item query
selects each card's labels one page deep, asking only `hasNextPage` and no cursor, so it has no way
to ask for the next page; it refuses rather than answer part of a card. `readIssue` reads one issue,
so it pages that issue's labels by cursor and answers every one. The two differ by design, not by
drift.

## The fakes

The fake `gh` and the in-process fake repository answer the default branch and files from the
test's `origin`. Git answers the file's mode, a missing commit and a missing path. Both fakes hold
issues as a seed field `issues`. The fake repository now takes `repo`, its own name, so its
pull-request read can name this repository as a head repository. Both hold a closed pull request
and one with a deleted head repository. The branch's pull-request read leaves both out, as GitHub
does.
