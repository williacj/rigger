# #509 — a worktree root spelled in another case

**The comparison that failed was `isWorktree`'s.** Measured at `74fd965` on APFS with git 2.54.0,
by a throwaway test outside the repository: for a workspace added at `<T>/worktrees/rigger-42`
over a disk holding `<T>/Worktrees`, Node's `realpathSync` printed the handed spelling,
`.../worktrees/rigger-42`, while `realpathSync.native` and `git rev-parse --show-toplevel` both
printed `.../Worktrees/rigger-42`. `isWorktree` compares git's top level with the path's real
path, so it answered `false`, and `cleared` refused card 42's own workspace as "something that is
not a workspace". `git worktree list` kept the spelling the worktree was added through, so
`registration` matched only while both makes used one spelling; under two spellings it would have
failed next.

**Fixing L0 alone would have introduced a defect.** With `realOrNothing` resolving by
`realpath(3)` and `cleared` still resolving the path by JavaScript's `realpathSync`, the check that
the path is not the worktree L1 was handed compared `.../worktrees/rigger-42` with `topLevel()`'s
`.../Worktrees/rigger-42`, read them as two, and went on to remove the handed worktree. The
handed-worktree test caught it before the fix in `cleared` and `topLevel` was written. At the base
that harm never happened only because `isWorktree` refused first.

**The fix is one rule in three places, not a new helper.** `realOrNothing` and `topLevel` in L0,
and `cleared` in L1, resolve by `realpathSync.native`, as `within` and #481's `judgeChecked`
already did. Nothing new was extracted: L0's comparisons share `realOrNothing` already, and L1's
two calls in `cleared` became one.
