# #1018 — the telemetry push, measured on a probe

The report is `docs/spikes/telemetry-push.md`. It measured both mechanisms, `git push` and `gh`'s
git data API, on both namespaces, `refs/heads/` and `refs/rigger/`, against the owner-made public
probe `williacj/rigger-spike-1018-probe`. Every stream it wrote was synthetic.

What we learned:

- **The stream's present size is a test fixture's.** Nothing emits yet, so the largest Rigger
  `events.jsonl` on the host is 1,243 bytes, left by a test run. At that size a push is all round
  trips: `git push` took about 1.6 s and the API about 2.4 to 2.6 s.
- **The forge admits no ruleset naming `refs/rigger/*`.** It refused both a `branch` and a `tag`
  target with "Invalid target patterns".
- **Through the API, the forge does not check fast-forward on `refs/rigger/`.** `force=false`
  replaced an unrelated commit there. On `refs/heads/` it refused one.
- **A refused API create does not name the rule.** It answered only "Reference update failed",
  where `git push` gave the GH013 rule text.
- **A stream-only commit started no workflow run on either namespace**, even with an unfiltered
  `on: push` workflow on `main`.

What failed:

- **My harness lost the API commit sha** on the first API write cells, so they ran with a malformed
  parent. I reran them on fresh refs and disclosed the extra writes on the card.
- **The classifier blocked one extra check that I added past the intent list**: an `~ALL` branch
  ruleset, to see whether a blanket rule reaches `refs/rigger/*`. I stopped, posted the block
  (1018#6453927183) and escalated the card. The owner ruled (M7-U7 Q32 (a), 1009#6454836792) that
  the report go ahead from the measured cells, with that check listed as not measured.
- **The lesson for the next spike: list every probe write in the intent before the run**, including
  the follow-up checks a refusal might prompt. A check added mid-run is the one a classifier stops.
