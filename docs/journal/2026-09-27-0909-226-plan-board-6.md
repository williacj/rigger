# #226 — `rigger plan` against board 6, staged with three throwaway cards

## What ran

At the owner's ruling of 2026-09-27, the maker filed three staging-only cards, #327, #328 and #329.
They were added to board 6 in Backlog and moved to Ready. Their positions were then read, and
Priority was set to Normal, High and Low respectively.

`rigger plan` then ran once. The engine was installed from a tarball `npm pack` made at `main`
`a0563bf03fe9235d7ba10da8427ad827dd3b0ea4`, installed outside every checkout. The working
directory was a fresh clone. The run exited 0 and printed:

```
rigger plan: from board 6, the next run would pull 3 cards, first pulled first
  pull    #328  change
  pull    #327  change
  pull    #329  change
```

That is the expected order posted on #226 before any Priority was set. All three cards were then
put back in Backlog with no Priority and closed as not planned. The pull request for #226 carries
every read.

## What we learned

- `gh project item-add` leaves the new item with no Status on board 6. Nothing puts it in a
  column; only an explicit edit does.
- `gh project item-list` returned the three new items at the end of the list, in the order they
  were added. Moving them to Ready did not change their positions, which were 82, 83 and 84
  before the move and after it. So on a board with no view sort, the position this card reads is
  add order rather than column order. Review r3-N2 asked this question; this read answers it
  only for items added and moved as these were.
- Because position order equalled issue order, two of the four naive orders coincided with the
  other two. Three distinct priorities still separate the expected order from all four. The
  card's acceptance anticipated this by choosing the values only after the positions were read.
