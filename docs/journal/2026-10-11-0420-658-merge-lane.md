ABOUTME: Records what card 658's merge lane taught: the claim with no slot, the re-read before a merge, and the
order of the merge's end against the Done move.

# A merge claim holds no slot, and that changes three things

#657 left `merge` answers unclaimed because a reservation that counted against the pull limit starved a Ready
card at concurrency one. The lane's claim holds no slot, so N does not bound it, and a Ready maker starts on the
sole slot while a merge waits. That is what the retargeted test at `test/loop.test.mjs` asserts, under a pull
given no limit, and it is the reading of r2 ruling 3 this card builds on. A limit that is given counts the merge
claim like any other, so `once` finishes one card. The first head exempted merges from the limit too, and the
section "A limit counts every card it finishes" records why that was wrong.

A claim with no slot also ends without a `slot.release`. The loop world inferred a claim's end from that event
alone, so its settling wait would have read a merge claim as held for ever. The world now ends a merge claim at
its `merge.end`, or at a `merge.start` the sink refused.

A merge freeing no slot fires no next pull, but another card's freed slot does. In `run`, a merge the forge
refused, say for a pending check, would then be pulled and refused again on every freed slot. The card is now
left out of the run's later pulls, so it waits for the next invocation, as the card's dimension row says.

# The lane reads the board again, not only the forge

The digest row needs the card's acceptance as it is when the lane reaches it, and only the board holds that. The
lane reads it through the read side's `readItems`, which the loop world serves straight from the fake board, so
the trigger count its settling wait compares against is unchanged. A mutation that hands L2 the card as claimed
rather than as read again reds the digest row and nothing else.

# The Done move follows `merge.end`

The dimension row for a refused `merge.end` after the forge merged says the next pull, not this one, moves the
card to Done. So L2's settle of the merge, the Done or Coding move, runs only once `merge.end` is recorded. A board
that refuses that move leaves the card for the next pull, which L2 answers as merged and moves without a second
merge call.

# A head that moved answers `judge`, not `merge`

The first draft of the re-run rows expected a moved head to come back as `merge` at another head. L2 answers it
`judge`: the reviewer's marker is at the old head, so the reviewer is owed one. The lane compares the action, the
pull request and the head alike, so either answer is `not merged`, and the test now expects what L2 answers.

# A limit counts every card it finishes, merges included

The first head exempted merge claims from the pull limit as well as from N. `once` passes a limit of one, so
one invocation merged two cards, against the README's "pull and finish one card". A merge holds no slot, but it
finishes a card, so a limit given now counts it like any other claim, while N still bounds only slots. The proof
of the N=1 maker beside a merge claim moved from `pull(1)` to `pull()`, under a grant on #658: with a limit of one
and the merge first in pull order, no maker could ever start beside it.

# A test double that drops an argument proves nothing about it

The loop world's workspace stand-in discards the head L3 hands it, so the conflict test passed with the head
removed. The head is now read by a workspace handle that records it, in a loop built over the world's board,
forge and L2.
