# #403 — A timed-out verb test ends its verb before sweeping its fixture

## What was built

`endsTheChildOnSigterm` registers its verb's teardown before it calls `holding(t)`, so the teardown
runs before `holding`'s sweep. The teardown is `ended(child)`, which kills the verb with `SIGKILL`
where it has not exited and settles on its `exit` event. A process that has exited spawns nothing,
so the sweep that follows finds every stand-in the verb started.

A test holds that order in place. It hands `startedAgainstHanging` a stand-in for `t` that collects
the teardown hooks, then runs them itself. After each hook it waits until the verb has exited or its
stand-in is ready, so a verb a hook left alive spawns its stand-in before the next hook runs. With
the two registrations swapped, it failed on three runs of three, naming the stand-in's and its
child's pids.

The fix stays in the test file. No other test file spawns a verb beside a scratch sweep, so there is
nothing to share through `test/process-fixtures.mjs`.

## What we learned

- **`t.after` hooks run in the order they are registered, and each is awaited.** A scratch probe
  with Node 26.5.0 on macOS 27.0 on 2026-09-28 registered three hooks on a test that timed out at
  50 ms, the second awaiting a 100 ms timer. They printed first, second, third.
- **A short timeout alone does not force the leak.** At the base, the verb had to spawn its stand-in
  between the sweep's last `pgrep` and the verb's `SIGKILL`. That window is milliseconds wide. The
  demonstration in the pull request holds the test file after each sweep's empty `pgrep` until the
  stand-in marks `ready`, or 5 s pass. With that, the base left five stand-ins and their `tail`
  children alive on every run, one for each test whose verb's command line does not name the scratch
  directory.
- **The in-spawn tests never leaked.** Their verb loads a module from the scratch directory, so its
  command line names that directory and the sweep kills the verb itself.
