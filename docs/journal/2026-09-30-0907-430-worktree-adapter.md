# #430 — The workspace adapter, and what its tests nearly missed

## What we learned

**Without the queue, the queue test first fails on git, not on its own assertion.** With the
queue mutated away and no retry yet written, the test's concurrent fetches lost git's own race:
`cannot lock ref 'refs/remotes/origin/main': is at … but expected …`. Once the retry existed, the
same mutant failed on the start and end times the stand-in recorded, which is what the test is for.

**A lost fetch race can be forced for real, but not every time.** A wrapper set as the fixture's
`remote.origin.uploadpack`, moving the local remote-tracking ref after `git-upload-pack` exits,
made the real `git fetch` fail with git's own words in 27 of 30 runs with git 2.54.0. Three runs
fetched clean, so it cannot hold a test. The test instead has the real git print the refusal, by
`git update-ref` from a value the ref does not hold, which meets the same lock check.

**A default-branch test can pass for the wrong reason.** Fetching `main` in place of `origin`'s
default branch passed the test for a changed default branch, because `main`'s history held the
other branch's commit. The test now moves `main` on from before that commit.

**`--no-track` does not show in the config when the start point is a commit id.** Git sets up no
upstream from a raw commit whatever the flag says (measured with git 2.54.0: the config was byte-identical
after an add without it), so the config comparison alone cannot tell the
flag is there. The test also reads the arguments a recording stand-in was sent.

## What nearly misled us

The repository's own fixture check refuses any `clone` or `worktree` a test runs outside
`test/git-repository.mjs`, a `worktree list` included. The fixture gained a bare clone, a worktree
made by git and the list, rather than the test running them itself.
