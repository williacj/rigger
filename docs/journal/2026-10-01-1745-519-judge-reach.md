# #519 — a judge's reach into `head`

**The route the ruling expected to win failed on the record, not on the behaviour.** Route A kept
`head`'s agent out of the session's context and never dispatched it. But Claude Code still listed
the agent in its `init` record, and item 1 asks about the record. Reading only the session's
answers would have passed it. The record also pointed to the real gap: the `Workflow` tool could
name the listed agent once asked, and only its own review step refused.

**No grant at all turned out to be the cleanest grant.** Route B gives `head` nothing a directory
grant gives, so nothing in `head` is discovered. The judge still reads, writes and runs commands
there through path-scoped permission rules. Those rules carry more weight than they appear to. They
are also what lets the session `cd` into `head`. A Bash rule allowing `cd <head>` was not enough
on its own.

**The transcript was the record that settled the context question.** #473 needed a stand-in
Messages API to see what reached a session. Here, each run's transcript under `~/.claude/projects/`
already held the `CLAUDE.md`, skill-listing, agent-listing, hook and MCP-instruction attachments,
so a marker search over it answered for every run, work runs included, at no extra cost. That
evidence lives in a directory cleanup removes, so it was extracted to the log before cleanup.

**Ask for the exit code in a form the tool prints.** The Bash tool printed `Exit code N` for a
failure and nothing for a success. One model reported 0 from that silence; another said it could
not see a code. A judge that reports a pass must say where its exit code came from.

**Ruling 4's Codex flags give `head` read but not write.** Without a `workspace-write` sandbox,
`--add-dir` grants nothing and says nothing. Neither sandbox made `head`'s `AGENTS.md` or skills
load.
