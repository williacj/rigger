# #608 — what no read shows is outside the record

**Why.** Each round of judging on L0's kill paths found one more case in which no read of the process
table could show a process that Rigger's kill had ended. Each found case became an exception row:
`R-STATE-20` for a joiner reaped between reads, then PR #592's `R-STATE-21` to `R-STATE-25` for a
process every answering read left out. The owner ruled O89 B: bound the record once, rather than
row by row.

**The bound.** `R-STATE-26` says the record of forced ends holds only what Rigger's reads of the
process table can show. A process that no read of its group, or of a dispatch's directory, showed
while each such read answered is outside `R-STATE-12`, `R-STATE-13` and `R-STATE-19`. A read that
fails is a different case, and those rows' own fallbacks still record the group or the directory in
its place. `R-STATE-20` is one instance of the bound, so it is withdrawn and `R-STATE-26` replaces it.
#592's case is another instance, as the second revision below shows, which is why the architect recommends closing #592.

**Ids.** `R-STATE-12`, `R-STATE-13` and `R-STATE-19` change only the id their citation names. What
must be true, read across the whole document, is carried by the new row. So they keep their ids, as
`R-STATE-17` and `R-STATE-10` did under #548 and the three rows did under #569.

**Architecture.** The Failure model now says that L0 records only what its reads of the table show,
for a group as for a directory, and that a process no read finds while every read answers is
recorded nowhere. It keeps the joiner as the example, and the code's `D16` rule 3 record.

**Order.** This is a proposal, and the owner's merge ratifies it and withdraws `R-STATE-20` (`D21`).
`R-STATE-26` lands claimed by no test, as `R-STATE-20` did. The Test quality decision-table card,
#606, claims it.

**What "answered" means (revision after #610's judges).** Both judges returned the acceptance under
`R-LOOP-6`: "while each such read answered" left "answered" undefined. The code refuses three
outcomes as reads that show nothing, and records the kill of the group for each:

- a read listing no process while signal 0 still reaches the group;
- a read leaving out the leader while signal 0 still reaches its pid;
- reads before the kill listing nothing for their bound.

The row now classes all three as reads "from which Rigger cannot read which processes the group
held", the phrase `R-STATE-12` and `R-STATE-19` already use. So the group's record those rows require
there still stands. The second revision below scopes this to the reads before the kill. The sentence
claiming the code records "each such case" under `D16` rule 3 now names only the case it records.

**Carried, not fixed here.** A live non-leader that one census read lists, and that every later read
hides, is killed with no record. That is a code gap against `R-STATE-12`, found by the engineer judge
on #610, and it goes to the Test quality milestone (O89 A).

**Second revision: reads before the kill, and after it.** Round 2 on #610 showed that the code holds a
read to signal 0 only before the kill, in the census and in `beforeKill`'s `timeout` case. After the
kill, `ended` and `emptied` take an empty listing as an empty group, and that is the right reading. A
process the kill ended still answers signal 0 while it exits, and may go unlisted. So the row now
holds only the reads before the kill to that rule, and says that after the kill a read shows what it
lists. The census's leader check moves to the Failure model, as the census's own. The last clause
reads "need not record it", because `beforeKill` names a hidden leader by signal 0 rather than by a
read. Under this text #592's whole case is covered again: its reads before the kill show the group
without the process, and its reads after the kill show what they list. The census and `beforeKill`
still treat a hidden leader differently before the kill, and the Test quality recording-core card
should settle that once.
