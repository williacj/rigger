# #471 — a one-turn wait is a guess about how long the loop takes

**A wait that releases a held dispatch has to know the loop is done starting.** The one-turn
`quiesce` assumed every start finishes within one turn. A board read that answers one turn later
breaks that: the first test in `test/loop.test.mjs`, rerun over such a board with its one-turn
waits, saw no dispatch held where it expected cards 1 and 2. Each wait now names what the test
reads next, such as how many dispatches are held, whether the pull has settled, or the reads the
board has answered.

**A condition that already holds is no wait at all.** `recordRun` in `test/report.test.mjs` first
waited until the maker held as many cards as had slots. After card 3 returned at minute 90, cards
4 and 5 were already held, so the condition held at once. The minute moved on before card 3's slot
release was recorded, and utilization read 1 rather than 0.8. The condition now also needs every
returned card's slot release to be recorded.

**A test's own timeout could not bound these waits on Node 20.** The first form found the
running test through `node:test`'s `getTestContext()`, so the waits needed no `t`. Node 20 has no
such export (`v20.20.2` answers `false`), and CI's `check (20)` failed on every file importing the
harness. Passing `t` in would have changed test and harness signatures no table granted, so the
card's author bounded the wait by a count of turns instead.

**The count rests on a measurement.** Across three full `npm test` runs with every wait recorded,
at one-minute loads of 5.9, 12.7 and 14.9 on 12 CPUs, 660 waits needed 0 turns 6 times, 1 turn
621 times and 2 turns 33 times. `WAIT_TURNS` is 1 000. A condition that never holds now fails
within that many turns, naming itself, where under a timeout-only bound a test with no timeout
hung its file.
