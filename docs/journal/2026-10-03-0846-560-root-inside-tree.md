# #560 — a worktree root inside the consumer's working tree is refused

**Why.** #557's engineer judge (N3) found that a `worktrees.root` inside the consumer's working tree
would put every workspace, every judge's directory and, from #555, every role's scratch directory
in the tree a maker stages from. For Codex that scratch directory holds a link to the owner's
`auth.json`. `validate` never learns the working tree, so the refusal sits at the start of the verb,
beside the guard on Rigger's own source tree.

**What it compares.** It compares the root's real path against the working tree's real path. Where
`top` is a linked worktree, it also compares against the main working tree, which git names as the
first entry of `git worktree list --porcelain`. That entry is used rather than the parent of
`--git-common-dir`, because a repository made with `--separate-git-dir` keeps its git directory
away from its working tree. A root inside either tree is refused.

**Why not `real`.** `doctor.mjs`'s `real` resolves an absent path through its nearest existing
parent, but it treats every failure as absence. The card wants any other failure refused, so
`once.mjs` gains `strictReal`, which walks up only on `ENOENT`. A link whose target is not there
also answers `ENOENT` from `realpathSync.native`. `lstat` tells it apart from a path that is
truly absent, and `strictReal` refuses it: the link is there, and its target could be inside the
tree.

**Mutations.** Three, each guarded and restored byte-exact, at a one-minute load between 17 and 20
(`uptime`, 2026-10-03), against `test/worktree-root-inside.test.mjs` (18 tests):
- `map(strictReal)` swapped for doctor's lenient `real` failed the four loop and dangling-link
  tests.
- Dropping the main working tree from the comparison failed the two linked-worktree tests.
- Comparing the paths as written (`resolve`) failed the eight symlink, absent-under-link, loop and
  dangling-link tests.
