ABOUTME: Records why the pre-post check is a `gh` shell function started from each session's shell,
and what the shells and the live runs showed that the design had not assumed.

# The pre-post content check

The check is a shell function named `gh`, so no directory is added to `PATH`. Under `PATH`, a
login profile that puts another directory first would decide which `gh` runs. The function
calls `post-check.mjs`, which decides the command's row, checks each part against #1486's rows,
and then starts the real `gh` with the bytes it checked. A file a flag names is copied before
the check reads it, and the copy is what `gh` is handed. Standard input is read once and passed
on as the input it checked. A file changed after the read therefore changes nothing that is sent.

A Claude Code session gets the function through `CLAUDE_ENV_FILE`, which its shell tools source
before each command. A Codex session gets it through `ZDOTDIR` and `BASH_ENV`, which name start
files that unset themselves and then define the function. Unsetting them is what keeps a node
child or a nested shell from inheriting a half-applied setup. Codex's shell snapshot would
otherwise replay the shell it captured at start, so the launchers disable both snapshot features.

Three things in the shells were not what the design assumed:

- **Bash on macOS:** bash 3.2 treats a socket on standard input as an rshd connection. It then
  reads `~/.bashrc` and skips `BASH_ENV`. Node's `spawn` gives a child a socket, so the host tests
  start their shells with standard input ignored, and the comment there says why.
- **Login zsh:** `zsh -lc` runs `path_helper`, which puts `/opt/homebrew/bin` ahead of a `PATH`
  set at launch. A read let through unchecked can then reach the real `gh`. This sits under the
  stated limit that `HOME` and `PATH` can redirect the check.
- **Command tables:** the tables of `gh` commands came from its reference, and a first parse of
  that reference missed the nested command headings. The tables were regenerated after the fix.

The live runs needed more than the card's plan:

- **The macOS keychain:** a Claude Code sign-in under a made `HOME` finds no login keychain, so
  the made home linked `Library/Keychains` to the owner's.
- **Prefix assignments:** zsh applies a command's prefix assignments in order. A
  `CLAUDE_CONFIG_DIR=$HOME/...` after `HOME=...` therefore named a directory under the made home.
  Full paths avoid this.
- **Shell tools:** a Claude Code session has two tools that run a shell, Bash and Monitor. The
  first live run tried only Bash and had to be run again.
- **Codex's state:** Codex writes the account id from `auth.json` into its session log and state
  database. That id identifies the account but grants nothing, unlike the id, access and refresh
  tokens, which no file of the made home held.
