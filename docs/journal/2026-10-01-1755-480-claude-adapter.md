# #480 — the Claude Code adapter

**The card first stopped on `reach`.** #473's report found that `--add-dir` loads a reached
directory's skills and agents. It found no withholder for the agents, and the only one for the
skills also withholds the consumer's own. I escalated the card as `ambiguous` before writing any
code. Ruling 8 on #467 kept `R-LOOP-14` and sent the route to a spike (#519) and a later card
(#520). The amended card has the adapter refuse `reach` by name, so the interface still takes it
and no judge can start with a grant that loads its `head`.

**An MCP tool the directory declared was refused at first.** The first live run's session called
the declared server's tool and got back "Claude requested permissions to use mcp__c480live__echo,
but you haven't granted it yet". The session still exited 0. #473's report had already found that
a `-p` session ignores an untrusted directory's own `permissions.allow` (c38) and honours the same
rule passed in `--settings` (c42). So the adapter now reads `allow`, `deny` and `ask` from the
directory's `.claude/settings.json` and passes them in `--settings`. It passes nothing else from
that block, since `defaultMode` or `additionalDirectories` would skip or widen the checks. This is
a judgment against the card's item on permission flags. The rules are the consumer's own, and the
CLI would apply them if the directory were trusted, so a judge should rule on it.

**Three built-in tools act through the owner's account on 2.1.287.** The live run's `init` record
listed `RemoteTrigger`, `PushNotification` and `DesignSync` beside the report's list. Under
`R-SAFE-9` they are withheld. Which tools act through the account is my judgment from what each
does, not a measurement. 2.1.287 also loads a third built-in plugin, `cc-plugin-plugin-authoring`.
Withholding the built-in plugins stays with the owner, as the report left it.

**Background-task output is not moved.** The report's route is the variable `CLAUDE_CODE_TMPDIR`.
`invocation` answers variables to unset and none to set (ruling 5), so the module records where the
output goes rather than passing the variable.

**Bundled skills are withheld with `--disable-slash-commands`.** That flag withholds every skill,
the consumer's own included. Ruling 8 holds that a role reads its skills by path, so the live run
through the installed package shows the consumer's skill by a `Read` of its file, and the start
record lists no skill at all.

**Two copies of L0's process adapter cannot share a process.** A live test file that imported this
checkout's `process.mjs` and the installed package's failed with `RangeError: Map maximum size
exceeded`. The error was thrown from the exit cleanup's `newListener` hook, because each copy puts
its own cleanup back ahead of the other's. The live runs now sit in two files. Production loads
one copy, so this lies outside the card's acceptance and is reported rather than fixed.

**Revision 1: every tool acting through the owner's account, every built-in plugin, and no
transcript.** #519's report found a `-p` session listing the owner's interactive sessions through
`ListAgents`, and offered `SendMessage` to message them. It also found 2.1.287's third built-in
plugin. I read each tool's own definition off a session's request, captured by a local stand-in
for the API with a dummy key, which sent nothing off the host. Five tools act through the owner's
sessions or login: `ListAgents`, `SendMessage`, `PushNotification`, `RemoteTrigger` and
`DesignSync`. Each is withheld unless the directory's own `permissions.allow` names it. All three
built-in plugins are switched off by `enabledPlugins` unless the directory's settings enable them,
and the live runs' start records now list no plugin. `--no-session-persistence` keeps a dispatch's
transcript out of the owner's `~/.claude/projects/`, and the live runs assert none is left.
