# #628 — wait for the killed leader

The O5 test reads the leader's process state after the caller exits. Its one read can still find a live leader and reject the run although the leader ends on a later turn. The failure recorded by PR #587's reviewer was `Rs`; it did not establish from a repeated read whether SIGKILL had reached that leader.

A new test schedules SIGKILL for the next event loop turn after observing a live leader. The old one read assertion failed with `SNs` under `npm test -- --test-name-pattern='the guard waits for a leader' test/never-stop.test.mjs` at `134d22f` on 2026-10-06, starting and ending at a one minute load of 19.62. The same test passed when the guard used `gone` at its default bound. That test demonstrates the wait, but delaying the test's signal is not a forcing of the O5 failure's suspected cause.

The guard now waits for the process to disappear and reports its last process state with the original message if it does not. A second test holds an unsignalled process outside L0's groups and checks that the guard rejects it after a shorter bound. Both test processes are registered for teardown by their child handles.

The original O5 guard did not fail in eight diagnostic file runs or 20 focused runs at `134d22f` on 2026-10-06. Those runs recorded a trace only on failure, so none of them supplies the trace the card later required. A second instrumented series used `npm test -- test/never-stop.test.mjs` at `134d22f` on 2026-10-06. All 20 whole-file runs passed 55/55 tests and recorded the group SIGKILL from `pairs`, the guard's first state, and repeated reads through gone on every run. `uptime` measured start loads of 4.22–23.57; the host had 0–3 `test/suite.sh` processes before each run. The first guard read was gone 8–40 ms after the logged SIGKILL in every run. The temporary instrumentation was removed after its logs were retained.

The historical `Rs` from PR #587 means that leader was runnable when the old guard read it. In this test, `holdingTwo` keeps the leader busy-looping, `CALLER` logs the group SIGKILL before `signalStandIn` calls the real `process.kill`, and `emptyAfterKill` prevents L0 from confirming its exit through a process-table read. The most supported cause is a sent SIGKILL that had not yet taken effect when the one-read guard ran. That scheduling step is an inference from the code and the historical `Rs`, not a failing-run trace from this card. Waiting through `gone` covers the transition; the unsignalled-live-leader test checks that a missing kill still fails.
